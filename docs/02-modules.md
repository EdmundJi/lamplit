# 02 · 代码怎么组织

继续用现有 Vue / Phaser 前端和 Spring Boot 后端，保持模块化单体。新版小街在 `town/companion` 按下面的边界实现，其余旧模块没有整体迁移。

## 四层就够了

先按业务模块组织，再在模块里分层。例如后端 `town/`：

```text
domain/        纯业务规则和状态，不碰数据库、HTTP、文件系统
application/   入住、专注、推进世界等用例，调用 domain 和接口
adapters/      数据库、LLM、文件及现有任务模块的接口实现
interfaces/    HTTP API、定时任务等入口，调用 application
```

依赖朝里走：`interfaces → application → domain`。外部能力的接口放在 application，由 adapters 实现、启动时装配。domain 不引用框架，也不自己读取时间；把时间和随机种子作为输入，方便测试与重放。

小镇内部主要有世界/地点、居民/行动、记忆/关系、用户意图这几块，先用清晰的类和子目录组织就好。不为分层创建微服务、大量空目录或万能接口。

## 小镇怎么动起来

**感知附近变化 → 找相关记忆 → 决定继续或调整计划 → 执行动作 → 记住结果。**

- 规则负责时间、基本需求、寻路、位置占用和动作执行，让生活一直能继续。
- LLM 负责计划、交谈、重要变化后的调整，以及从经历中形成少量看法。走每一步、读书每一秒都不需要调用模型。
- 初始世界先有一份共同历史，再给各居民生成各自知道的记忆，预运行后存成开局。入住时复制独立存档，刷新不重置。
- NPC 只获得实际看见、听见或被告知的信息。记忆保留来源，把事实、转述和推测分开。
- 模型提出动作后，规则检查它是否可执行。失败或超时就继续已有计划，不能让世界卡住。

### 谁先动：规则是下意识，模型是解释

上面那条链讲的是"需要想一想"的情形。但人大多数时候不想——习惯先动手，大脑事后补一个
说法，而那个说法经常不是真正的原因。所以这一层是分开的：

- **规则可以直接让人做事**，不问模型：人设里写死的小动作（心里不舒服去擦桌子、
  被打断就闭嘴）、把人带去某处的习惯（复习就去咖啡馆窗边）。这些动作**不推进任何
  世界状态**——擦桌子不产生任何后果，这正是重点。做了就登记一条"行为"，
  登记的内容只写旁观者看得见的东西，**绝不写动机**：规则不知道任何人为什么做任何事。
- **模型事后给出他自己的说法**，攒够几条一起问。说法落成一条推测型记忆，
  并覆盖他的当前想法——从此那就是他关于自己知道的东西，也是下一次决策会读到的东西。
  说法允许是错的、防御性的、被自己的"应该"扭曲的。
- **没有最后这一步，模型就只是一个每次调用都要付钱的旁白器。** 解释必须能回头改变行为，
  这个环才闭得上：行为 → 说法 → 记忆 → 信念 → 下一次的默认动作。

同一条原则也管社交：规则只负责**制造决策时机**（把两个人放到面对面），
不负责决策本身（要不要开口、要不要坐过去，模型自己答，"看见了但没走过去"是合法答案）。

例如“想看看花”：入口接收念头 → 用例保存意图 → 规则结合当前专注安排决定时机，必要时问模型 → 检查位置与意图是否仍有效 → 执行动作 → 写下实际结果。取消后不执行迟到的模型回复。

## 记忆存在哪

居民的记忆不再挤在世界存档那一列 JSON 里，改成一人一个目录：一个事实一个文件，带简短的头部说明，正文里可以引用别的记忆。物理隔离让各人的记忆不会串味，也让开发期的上帝视角能直接展示原文，人能读、能改、能删。

写入分两步：每件事先用规则廉价地记一条原始日志，模型只用在“各自把经历提炼成看法”那一步。这不是为了省钱，是为了可控可测——出了问题能回溯到客观的原始事件，而不是只剩四份各执一词的转述。旧的记忆和好感不删除，只标记为已被取代，这样“为什么变了”永远答得出来。

隔离要落在存储层，不能靠提示词。每条记忆带主人，检索接口不接受不带主人的查询——共享记忆池加应用层过滤是已知会出事的做法。记忆进入模型时作为数据传，不拼进指令区。

代价要一起认下来：世界状态从此不全在数据库里。备份、导出、注销清理、容器挂载都要覆盖到这批文件——尤其注销，必须连同该用户的记忆目录一起删掉，不能让刚补好的洞重新漏。写文件与写存档之间也要说清楚谁是权威、对不上时以谁为准。

## 几个要守住的边界

- 后端保存权威世界状态，前端负责画面、声音和即时操作反馈。多个标签、在线推进和离线恢复不能重复制造同一件事。
- 真实任务复用现有任务模块；小镇关联任务，但不自己发明完成规则，更不能自动代勾。
- 只把执行过的事记为事实。用户私密任务内容不会自动成为 NPC 的谈资。
- 日夜贴近用户时区，专注按真实时长。页面关闭后先做有限的日程补算，不持续无限调用模型或编造离线长剧情。
- 模型请求不占着长数据库事务；返回后核对状态，过期的决定丢弃。

## 从现有代码慢慢改

新版后端入口在 [town/companion](../backend/src/main/java/com/betterself/growth/town/companion)，前端入口在 [companion](../frontend/src/modules/companion)。世界存档与旧小镇独立，新的 HTTP 入口只调用新版推进；旧社会与反思定时任务默认停用。模型通过异步接口读取居民各自的感知与记忆，返回后校验版本再提交行动。

前端将场景绘制数据与完整故事数据分开，稳定的绘制输入不会因日记或记忆刷新而重建场景。世界状态和任务结果由后端决定；Phaser 负责路径呈现和动画，DOM 负责清晰的资料与对话阅读。

旧的后端 town 模块与前端 `modules/town` 已经整体删除：它们不再可达，而且旧的单聊会把真实任务标题原文拼进模型提示词。仍在用的碰撞、寻路、行走和声景四个工具搬到了 `frontend/src/shared/scene`。

先挑一条完整用例，把纯规则抽出来，通过接口复用现有存储和模型，再让 HTTP/任务入口调用它。不为了目录整齐一次重写整个系统；新旧推进逻辑也不要同时写同一个世界。

前端同样把纯计算、操作编排、HTTP/Phaser/Web Audio 和页面入口分开，但不复制一套服务端社会模拟。

修改哪里就验证相关行为，尤其是任务隔离、取消、记忆来源、重复推进和真实声画。具体方案、分工和检查结果在会议与 PR 中讨论记录。
