# 成长小镇：前后端接口约定（工作中）

这份约定给并行开发的各个部分使用。后端在 `backend/src/main/java/com/betterself/growth/town/` 实现，前端在 `frontend/src/modules/town/`。
凡是标了「假定」的字段，前端必须容错（404 或缺字段时退回到现有行为）。

## 1. 小镇读模型 `GET /api/v1/town`

```json
{
  "localDate": "2026-09-05",
  "serverTime": "2026-09-05T02:10:00Z",
  "unread": 2,
  "soloGrowth": false,
  "residents": [
    {
      "publicId": "01H...", "displayName": "育德", "level": 5, "totalExperience": 520,
      "dominantDimension": "KNOWLEDGE", "longestStreak": 12, "title": "晨型人", "self": true,
      "timezone": "Asia/Shanghai",
      "schedules": [
        { "publicId": "01H...", "title": "背单词 20 分钟", "status": "PLANNED", "roleCode": "STUDENT", "roleName": "学生",
          "plannedStartAt": "2026-09-05T11:00:00Z", "plannedEndAt": "2026-09-05T11:20:00Z", "estimatedMinutes": 20, "difficulty": 2 }
      ]
    }
  ]
}
```

- 所有响应都包在 `{ data, requestId, timestamp }` 信封里，前端 `api.get` 已经解包。
- `status` 取值：`PLANNED` `IN_PROGRESS` `DONE` `PARTIAL` `DEFERRED` `SKIPPED` `EXPIRED`。
- `dominantDimension` 可能为 `null`。`title` 只有自己有值。
- `soloGrowth` 为 true 时 `residents` 只有自己。
- 前端把这个响应映射成现有的 `TownResident`，并新增 `schedules` 与 `timezone` 字段。旧的多请求拉法（`/me/profile` + `/friends/...`）作为 `GET /town` 返回 404 时的兜底保留。
- 前端每 30 秒轮询一次；页面不可见时暂停。对比前后两次的 `schedules[].status`，出现 `DONE`/`PARTIAL` 就触发庆祝。

### 场地映射（前端规则，写在 `building-kit.ts`）

| 任务 `roleCode` | 小人去哪 | 到达后动作 |
| --- | --- | --- |
| `STUDENT` | 学院门口 | 读书 |
| `WORKER` | 学院门口 | 看手机 |
| `FITNESS_USER` | 学院左侧篮球场 | 站立（idle） |
| `EMOTIONAL_SUPPORT_USER` | 广场喷泉旁的长椅 | 站立 |
| 其他 / 无 | 自己家门口 | 站立 |

日程驱动规则：取 `plannedStartAt` 到 `plannedEndAt`（没有结束时间就按 `estimatedMinutes`，至少 30 分钟）。当前时间落在区间内且状态是 `PLANNED` 或 `IN_PROGRESS` 时小人应该在场地；`DONE`/`PARTIAL` 的任务在结束后 2 小时内小人留在场地，之后回家。其余时间在家门口活动。区间要按 `serverTime` 与本地时钟的差值校准。

## 2. NPC 对话

- 历史：`GET /api/v1/town/npc/{npc}/messages` → `MessageView[]`
  `{ publicId, role: "USER"|"ASSISTANT", content, options: [{label}], actions: [{type, scheduleId, label, taskTitle}], status: "COMPLETED"|"BLOCKED", createdAt }`
- 发送：`POST /api/v1/town/npc/{npc}/chat:stream` body `{ "message": "..." }`，SSE 事件顺序：
  - `meta` `{ npc, messagePublicId, model, riskLevel }`
  - `delta` `{ text }`（多次，逐字追加）
  - `safety` `{ riskLevel, message }`（可选，L2/L3 时出现，此时没有 delta）
  - `done` `{ messagePublicId, status, options: [{label}], actions: [{type, scheduleId, label, taskTitle}] }`
  - `error` `{ code, message }`
- `npc` 取值：`GUIDE`（小助）、`POSTMAN`（邮递员）。路径里用大写代码。
- 前端复用 `shared/api/sse.ts` 的 `postSse`。
- 配额：后端每日限制，超限返回 429 一类错误，前端显示「小助今天说累了，明天再聊」。

### 动作执行（前端负责）

| `type` | 前端行为 |
| --- | --- |
| `START_TASK` | `POST /task-schedules/{scheduleId}/events` `{ eventType: "STARTED" }` |
| `COMPLETE_TASK` | 同上，`eventType: "COMPLETED"` |
| `DEFER_TASK` | 同上，`eventType: "DEFERRED"`，附加字段与 `TodayView.vue` 里的推迟逻辑一致（先看那里怎么传 `deferredStart`） |
| `SKIP_TASK` | 同上，`eventType: "SKIPPED"` |
| `OPEN_TODAY` / `OPEN_GOALS` / `OPEN_AI` / `OPEN_FRIENDS` | `router.push('/today' | '/goals' | '/ai' | '/friends')` |

任务类动作都要带 `Idempotency-Key` 请求头（`randomUUID()`），执行后触发小镇数据刷新。

## 3.5 小镇社会：限知与传播（M1）

一人一镇：每个用户有自己独立的 18 个 NPC 与事实库，NPC 的知识只关于「一个玩家 + 其他 NPC」。

### `GET /api/v1/town/npcs`

返回本用户小镇的名册。首次调用会顺带把 18 个 NPC 落地（幂等）。

```jsonc
{ "data": {
    "npcs": [ {
      "code": "KE_YUN", "displayName": "柯云",
      "layer": 2,                       // 1=会索取回应 2=可搭话不索取 3=纯背景
      "sprite": "c01",                  // 前端 spritesheet key 的后半段
      "dimension": "KNOWLEDGE",         // 二层 NPC 绑定的维度；一层/三层为 null
      "interests": { "KNOWLEDGE": 0.4, "HEALTH": 0.1, "CAREER": 0.2, "RELATIONSHIP": 0.2, "WELLBEING": 0.1 },
      "affinityToPlayer": 0.42,
      "mood": { "valence": 0.3, "energy": 0.6 },
      "schedule": [ { "startHour": 6, "endHour": 9, "place": "home", "activity": "idle" } ],
      "dayPlan": {
        "date": "2026-09-06",
        "errands": [ { "place": "gym", "activity": "idle", "startMinute": 420, "endMinute": 480, "priority": 2, "origin": "RHYTHM" } ],
        "legs": [ { "fromPlace": "home", "toPlace": "gym", "departMinute": 405, "arriveMinute": 420 } ]
      },
      "talkingPoints": [ { "factId": "01J...", "text": "听说小吉最近老往健身房跑", "hops": 2, "salience": 0.61 } ]
    } ],
    "initiativeBudget": { "limit": 3, "used": 1 }
} }
```

- `place`：`home` | `academy` | `gym` | `cafe` | `park` | `plaza` | `street`
- `activity`：`idle` | `walking` | `reading` | `sit` | `phone` | `watering` | `chopping` | `fishing` | `harvesting` | `digging`
- `schedule` 覆盖 0~24 点、无空洞、按 `startHour` 升序；由 `(npc_code, 日期)` 确定性生成，前后端算出来的是同一份。**M7 起同时下发 `dayPlan`**（分钟级 errands+legs），`schedule` 原样保留、口径不变——细节见下方「M7」一节。
- `initiativeBudget` 是护栏 A：全镇每天主动搭话的总次数上限，小助优先。**M7 起 `used` 是真实持久化的值**（按 `(user_id, 当地日期)` 落库），不再是前端内存里的临时计数——见下方「护栏 A 的持久化」。

### `GET /api/v1/town/npc/{code}/talking-points`

```jsonc
{ "data": { "code": "KE_YUN", "displayName": "柯云",
            "points": [ { "factId": "01J...", "text": "...", "hops": 2, "salience": 0.61 } ] } }
```

镇上没有这个 code 时 404 `TOWN_NPC_NOT_FOUND`。

**限知的两条硬性表现**（有集成测试钉死，见 `TownSocietyIT`）：

1. 只返回该 NPC 自己 `town_npc_knowledge` 里 `no_relay = 0` 的条目。小助（GUIDE）全知，但它的每一条都是 `no_relay = 1`，所以**它的 `points` 恒为空**——它对你说话，不对外传话。
2. 玩家事实进入 `town_fact` 前必须过 `TownNpcPerception` 模糊化，落库的 `payload.text` 里**不含任何阿拉伯数字、任务标题或具体时刻**。

### 每晚的传播 job

`TownSocietyJob`（cron `app.town.society-cron`，默认 03:45，排在反思 03:15 之后）逐用户跑 `TownSocietyService.runNightly`：采集事实 → 目击判定（在场轨迹 × NPC 日程）→ 传播模拟 → 批量生成每一手的走样文本 → 更新亲密度。整晚一个事务，重跑幂等（靠 `town_fact` 的 `(town_user_id, subject_kind, subject_ref, kind, occurred_on)` 唯一键）。

走样文本由 `TownRetellGenerator` 生成：默认走 Qwen 批量结构化调用（scene `TOWN_RETELL`，≤20 条一批），**任何异常、解析失败、或输出里出现数字/超长/key 对不上，都逐条回退到确定性模板**，所以没有 key 的环境也能跑通整条链路。

## 5. 接真实模型时的几个坑

- **流式回复的尾巴**：NPC 先说完口语部分，再写 `§§` 那行 JSON（选项与动作）。模型写这行的耗时波动很大，实测 2s～95s，所以前端在正文到齐后就重新开放输入框，并提示「XX 正在挑下一步…」；用户此时再发一句会中断上一条流，已读到的正文照常留在记录里。
- **provider 中途掉线**：正文已经流出去之后如果 provider 抛错（网关超时、524 等），后端不再把整条回复换成错误提示，而是把已收到的正文存下来并照常发 `done`，只丢掉选项与动作（`TownNpcTruncatedStreamIT`）。
- **超时分开配**：非流式用 `QWEN_TIMEOUT`，流式用 `QWEN_STREAM_TIMEOUT`（默认 PT130S，需与 `TOWN_CHAT_STREAM_TIMEOUT` 一致或更短）。
- **`response_format` 不是所有网关都支持**：某些 OpenAI 兼容网关收到 `{"type":"json_object"}` 会一直挂住直到 524，导致「每晚反思」「目标草案」这类结构化调用超时。这类网关把 `QWEN_JSON_MODE=false` 即可——schema 仍然写在 prompt 里，返回值走已有的去代码块 + 修复重试逻辑。

## 6. 位置连续性（在场坐标）

小镇里的人不能瞬移：刷新页面、切换设备、别人上线，看到的都应该是「他刚才在哪、正往哪走」，而不是按日程重新算出来的一个新落点。

### 6.1 数据

服务端为每个用户保存一份最近位置：

| 字段 | 说明 |
| --- | --- |
| `x` / `y` | 世界坐标（像素，小镇坐标系；室内场景各自坐标系） |
| `facing` | `up` / `down` / `left` / `right` |
| `scene` | `town`、`academy`、以及未来的室内房间 id |
| `updatedAt` | 服务端写入时间（UTC） |

### 6.2 上报

`POST /api/v1/town/presence`，请求体 `{ x, y, facing, scene }`。

- 客户端**节流**上报：停下来时报一次；移动中最多每 3 秒一次；页面隐藏或离开时报最后一次。
- 服务端做**速度校验**：与上一条记录比较，位移不得超过 `RUN_SPEED(264 px/s) × 间隔秒数 × 1.5` 的余量；超出则**夹到**允许的最大位移处并照常写入（而不是拒绝），避免网络抖动或长时间离线导致写入失败。跨 `scene` 时不做速度校验。
- 返回服务端最终采纳的 `{ x, y, facing, scene, updatedAt }`，客户端以返回值为准。

### 6.3 读取

`GET /api/v1/town` 的每个 resident 增加：

```json
"presence": { "x": 1234, "y": 832, "facing": "left", "scene": "town", "updatedAt": "...", "stale": false }
```

- `stale`：`updatedAt` 距今超过 10 分钟即为 `true`。
- 没有任何记录时 `presence` 为 `null`。

### 6.4 客户端连续性规则

1. **自己**：进入小镇时，若 `presence` 存在且 `scene` 匹配，就从该坐标出生；否则回到自家门口。
2. **别人**：轮询拿到新坐标后**不允许直接 setPosition**，一律设为行走目标，让小人自己走过去；距离过大（超过一屏）时才允许淡出淡入，并且要有明确的视觉过渡。
3. **stale 的居民**：按日程摆放，但仍然从上一次已知位置**走过去**，不瞬移。
4. 位置只用于呈现，不参与任何奖励计算；服务端的速度夹取只为防抖与防作弊，不作为惩罚。

## 7. NPC 的一天：节律、行程与相遇类型（M7）

承 §3.5，本节是 `dayPlan` 字段与相遇判定改造的完整约定，前后端已在 `CONTRACT-M7.md` 里锁定字段名与权重，这里是那份契约在本文档里的落点。

### 7.1 节律 → 当天行程（后端内部，不经 API）

`town_npc.rhythm`（JSON）是这个 NPC"平常的一天"：几点起、几点睡、常去哪几处、每处待多久。由五维度兴趣与性格（`share_drive`/`curiosity`）在建号时算好写入（`TownNpcRhythm.defaultFor`），此后不再变——18 个人各自不同，互不雷同。

当天的 `dayPlan` = 节律 ± 当天偏离，偏离的输入来自：

| 来源 | 效果 |
| --- | --- |
| 心情（`town_npc_mood.valence`） | 低于 -0.2 起减少外出行程，越低删得越多 |
| 天气 | 下雨天缩短户外（`park`/`plaza`/`street`）行程的停留时长 |
| 对玩家的亲密度 | 高于 0.5 时有概率顺路加一件不打紧的小事（`priority: 0`） |
| `town_event`（M4，暂未接线） | 必定插入一条 `priority: 2` 的行程；`town_event` 表建好前，这一路输入恒为空集合 |

同 `(npc_code, date)` 恒等、换一天会变——由 `seed(npc_code, date)` 决定，不在运行时掷骰子。

### 7.2 相遇类型（后端内部，传播权重是硬约定）

相遇判定不再是"同一时段同一地点"，改成两条分钟级时间线（`errands` ∪ `legs`）按 `positionAt` 逐点比对，分三类：

| 类型 | 条件 | 传播权重乘子 |
| --- | --- | --- |
| `CO_LOCATED`（同处停留） | 两人同一时刻都 `AT` 同一地点 | 1.0 |
| `EN_ROUTE`（路上相遇） | 两人同一时刻都在 `WALKING`，且路线共享至少一个端点 | 0.6 |
| `PASSING`（擦肩） | 一人 `AT` 某处，另一人途经该处（该处是其 `WALKING` 腿的起点或终点） | 0.3 |

`home` 在任何一类里都不算相遇。保证：其余条件相同时 `P(CO_LOCATED) ≥ P(EN_ROUTE) ≥ P(PASSING)`。这一改造只影响夜间 job 内部如何生成相遇序列与之后的传播结果，不新增 HTTP 字段。

### 7.3 护栏 A 的持久化

`initiativeBudget.used` 现在按 `(user_id, 当地日期)` 落在 `town_initiative_budget` 表里，不再是前端内存里刷新即归零的计数。

`POST /api/v1/town/initiative/consume`：谁调用谁把共享额度消费一次，返回消费后的 `{ "limit": 3, "used": 1 }`。超过 `limit` 之后 `used` 不再往上涨（`used == limit`，是饱和状态而不是报错）——按 `(user_id, local_date)` 幂等，同一天重复调用不会把 `used` 推过 `limit`。

前端接线：引擎在 `maybeInitiate` 里先按本地乐观值扣一格（这一帧的判断要立刻生效），同时通过
`TownHandlers.onInitiativeSpent` 通知外壳；外壳调 `townNpcStore.consumeInitiative()` 上报，再把
服务端返回的权威值经 `TownGame.setInitiativeBudget` 覆盖回去。端点返回 404（尚未部署）时保持
本地值不变——宁可放宽，也不该因为后端没上线就让 NPC 一句话都不说。

## 7.4 整晚流水线的执行顺序

`TownSocietyJob` 对每个小镇按这个顺序跑四步，顺序不是随便排的：

```
1. TownEventService.runNightly      活动 + 请柬
2. TownSocietyService.runNightly    事实 → 目击 → 传播 → 转述 → 亲密度
3. TownConfidantService.runNightly  树洞回信
4. TownMigrationService.runNightly  迁徙 + 旅人
```

- **活动必须排在社会模拟之前**。它今晚建的 `town_event` 起始时间就在今天，而当天行程（M7-3）
  要把这场活动插成一条 `priority=2` 的安排。晚于社会模拟执行的话，夜里推出的相遇序列里没有
  这场活动、白天 `GET /town/npcs` 却算得出有——前后端两份日程分叉，§3.5「两边算出来的必须是
  同一份」这条地基就不成立了。代价只是请柬排序用的是昨晚的亲密度，而亲密度按天缓慢变化，肉眼无差。
- **迁徙排在最后**，因为它会改动名册。它同时会写进对方的小镇，但**当天搬到的人不参与该镇当晚的
  模拟**（依据是 `town_migration` 当天的记录，不是建号时就写好的 `town_npc.settled_at`），
  所以 A、B 两个用户谁先被 job 扫到都算得出同一份结果。新面孔当天在名册里看得见，只是今晚
  还没跟谁说上话。

## 8. 事件、信件、迁徙、树洞笔友（M4）

对应 plan.md M4-1/M4-4/M4-6/M4-7/M4-8。后端在 `TownEventService` / `TownLetterService` /
`TownConfidantService` / `TownMigrationService` 实现，接口全部新开在 `TownSocialController`
（不改 `TownController`）。**信件与活动只入叙事，不入数据**——这几条接口不发经验、不发成就，读信、
办活动、搬家都不产生任何可兑换的数值。

### 8.1 `GET /api/v1/town/letters`

收件箱：树洞长信（`LONG`）、NPC 短笺（`NOTE`，当前版本暂无生产者，但读写路径已支持）、活动请柬
（`INVITE`）三轨都在这里，只列出已经到投递时间的信。

```jsonc
{ "data": {
    "letters": [ {
      "publicId": "01J...",
      "senderKind": "NPC",              // "NPC" | "CONFIDANT"
      "senderRef": "KE_YUN",            // CONFIDANT 时为 null
      "senderName": "柯云",              // CONFIDANT 时固定为「树洞笔友」
      "kind": "INVITE",                 // "LONG" | "NOTE" | "INVITE"
      "body": "「柯云」在广场张罗了一场聚会，要不要一起来？",
      "deliverAt": "2026-09-06T10:00:00Z",
      "readAt": null,
      "createdAt": "2026-09-06T10:00:00Z"
    } ],
    "unreadCount": 1
} }
```

### 8.2 `POST /api/v1/town/letters/{id}/read`

把一封信标记为已读；已经读过的再读一次也返回 200（幂等）。信不存在或不属于当前用户时 404
`TOWN_LETTER_NOT_FOUND`。

### 8.3 `POST /api/v1/town/confidant`

写信寄给树洞笔友。`{ "message": "..." }`；消息为空/全空白时 400 `TOWN_CONFIDANT_EMPTY`。

- 写信本身**不产生回信**、**不碰 `town_fact`/`town_npc_knowledge` 半行**——树洞与小镇八卦是两条
  完全不共享查询路径的存储（plan §3.4 第 6 条）。
- 回信只在夜间流水线里生成，且只回复「写于今天之前」的来信——这就是"隔天"：今天写的信最早
  也要等下一次夜间 job（也就是明天）才会出现在收件箱里，回信只倾听、回应，绝不给建议，且
  **prompt 里除了来信正文之外不注入任何玩家数据**（不含目标、任务、连续天数）。
- 回信走 Qwen（`QwenConfidantReplyGenerator`，scene `TOWN_CONFIDANT`），任何异常/校验不过都回退到
  确定性模板（`TemplateConfidantReplyGenerator`），且有总时长预算，绝不放在数据库事务里。

### 8.4 事件与请柬（无独立读接口，体现在 `town_event`/`town_invitation`/信件里）

`TownEventService.runNightly` 每天最多让第二层的一个 NPC 办一场活动（场地固定复用
`plaza`/`park`/`cafe`），按亲密度降序给玩家与其他 NPC 发请柬（`town_invitation`），玩家额外收到
一封 `kind=INVITE` 的信。谁办、办不办由 `P(办) = f(share_drive, 朋友数, mood.valence)` 决定
（`TownEventServiceTest` 有 30 天模拟：不会连续一周冷场，也不会天天办）。

### 8.5 迁徙与旅人（无独立读接口，体现在名册 `GET /api/v1/town/npcs` 与信件里）

`TownMigrationService.runNightly`：

- **迁徙**（M4-6）：仅在互为好友的两个小镇之间、仅第三层背景居民、交换制（各出一个、各进一个，
  每镇恒定 18 人），稀疏触发（期望 1~2 周一次），冷却 21 天（`town_npc.settled_at`）。带着一条
  已经模糊化过的「节奏印象」当作自己的往事讲给新镇听，标记 `origin_town_user_id`，且用更高的
  `hops` 让它按现成的衰减公式更快淡出（两周内基本听不到了）。原镇上对这个槽位的好感转成
  `regard_kind = 'MISS'`；换人之后这个槽位的相处记录清零重来。
- **路过的旅人**（M4-7）：没有任何好友的用户会持续有一位不属于任何人的 NPC（`npc_code=TRAVELER`）
  陪着，讲泛化的、不涉及任何真实用户的传闻，停留几天后自动离开（离开时清掉它的所有痕迹）。一旦
  用户有了好友，不再补充新的旅人。

### 8.6 红线自查（plan §2.5 / §3.4）

- 以上所有接口都不出现 `regard`/`regard_kind` 字段，也没有任何「谁暗恋谁」的确认入口。
- NPC 从不因为信件/活动/迁徙对玩家产生 `regard`；玩家侧的 `town_bond` 行结构上就不允许写入
  `regard`（数据库 CHECK 约束）。
- 信件、活动、迁徙都不占用护栏 A 的每日主动性预算——收件箱是玩家主动打开看的，不是 NPC 跑来打断。
