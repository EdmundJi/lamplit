# 成长小镇：前后端接口约定（工作中）

这份约定给并行开发的各个部分使用。后端在 `backend/src/main/java/com/betterself/growth/town/` 实现，前端在 `frontend/src/modules/town/`。
凡是标了「假定」的字段，前端必须容错（404 或缺字段时退回到现有行为）。

## 1. 小镇读模型 `GET /api/v1/town`

```json
{
  "localDate": "2026-09-05",
  "serverTime": "2026-09-05T02:10:00Z",
  "unread": 2,
  "soloGrowth": false,
  "residents": [
    {
      "publicId": "01H...", "displayName": "育德", "level": 5, "totalExperience": 520,
      "dominantDimension": "KNOWLEDGE", "longestStreak": 12, "title": "晨型人", "self": true,
      "timezone": "Asia/Shanghai",
      "schedules": [
        { "publicId": "01H...", "title": "背单词 20 分钟", "status": "PLANNED", "roleCode": "STUDENT", "roleName": "学生",
          "plannedStartAt": "2026-09-05T11:00:00Z", "plannedEndAt": "2026-09-05T11:20:00Z", "estimatedMinutes": 20, "difficulty": 2 }
      ]
    }
  ]
}
```

- 所有响应都包在 `{ data, requestId, timestamp }` 信封里，前端 `api.get` 已经解包。
- `status` 取值：`PLANNED` `IN_PROGRESS` `DONE` `PARTIAL` `DEFERRED` `SKIPPED` `EXPIRED`。
- `dominantDimension` 可能为 `null`。`title` 只有自己有值。
- `soloGrowth` 为 true 时 `residents` 只有自己。
- 前端把这个响应映射成现有的 `TownResident`，并新增 `schedules` 与 `timezone` 字段。旧的多请求拉法（`/me/profile` + `/friends/...`）作为 `GET /town` 返回 404 时的兜底保留。
- 前端每 30 秒轮询一次；页面不可见时暂停。对比前后两次的 `schedules[].status`，出现 `DONE`/`PARTIAL` 就触发庆祝。

### 场地映射（前端规则，写在 `building-kit.ts`）

| 任务 `roleCode` | 小人去哪 | 到达后动作 |
| --- | --- | --- |
| `STUDENT` | 学院门口 | 读书 |
| `WORKER` | 学院门口 | 看手机 |
| `FITNESS_USER` | 学院左侧篮球场 | 站立（idle） |
| `EMOTIONAL_SUPPORT_USER` | 广场喷泉旁的长椅 | 站立 |
| 其他 / 无 | 自己家门口 | 站立 |

日程驱动规则：取 `plannedStartAt` 到 `plannedEndAt`（没有结束时间就按 `estimatedMinutes`，至少 30 分钟）。当前时间落在区间内且状态是 `PLANNED` 或 `IN_PROGRESS` 时小人应该在场地；`DONE`/`PARTIAL` 的任务在结束后 2 小时内小人留在场地，之后回家。其余时间在家门口活动。区间要按 `serverTime` 与本地时钟的差值校准。

## 2. NPC 对话

- 历史：`GET /api/v1/town/npc/{npc}/messages` → `MessageView[]`
  `{ publicId, role: "USER"|"ASSISTANT", content, options: [{label}], actions: [{type, scheduleId, label, taskTitle}], status: "COMPLETED"|"BLOCKED", createdAt }`
- 发送：`POST /api/v1/town/npc/{npc}/chat:stream` body `{ "message": "..." }`，SSE 事件顺序：
  - `meta` `{ npc, messagePublicId, model, riskLevel }`
  - `delta` `{ text }`（多次，逐字追加）
  - `safety` `{ riskLevel, message }`（可选，L2/L3 时出现，此时没有 delta）
  - `done` `{ messagePublicId, status, options: [{label}], actions: [{type, scheduleId, label, taskTitle}] }`
  - `error` `{ code, message }`
- `npc` 取值：`GUIDE`（小助）、`POSTMAN`（邮递员）。路径里用大写代码。
- 前端复用 `shared/api/sse.ts` 的 `postSse`。
- 配额：后端每日限制，超限返回 429 一类错误，前端显示「小助今天说累了，明天再聊」。

### 动作执行（前端负责）

| `type` | 前端行为 |
| --- | --- |
| `START_TASK` | `POST /task-schedules/{scheduleId}/events` `{ eventType: "STARTED" }` |
| `COMPLETE_TASK` | 同上，`eventType: "COMPLETED"` |
| `DEFER_TASK` | 同上，`eventType: "DEFERRED"`，附加字段与 `TodayView.vue` 里的推迟逻辑一致（先看那里怎么传 `deferredStart`） |
| `SKIP_TASK` | 同上，`eventType: "SKIPPED"` |
| `OPEN_TODAY` / `OPEN_GOALS` / `OPEN_AI` / `OPEN_FRIENDS` | `router.push('/today' | '/goals' | '/ai' | '/friends')` |

任务类动作都要带 `Idempotency-Key` 请求头（`randomUUID()`），执行后触发小镇数据刷新。

## 5. 接真实模型时的几个坑

- **流式回复的尾巴**：NPC 先说完口语部分，再写 `§§` 那行 JSON（选项与动作）。模型写这行的耗时波动很大，实测 2s～95s，所以前端在正文到齐后就重新开放输入框，并提示「XX 正在挑下一步…」；用户此时再发一句会中断上一条流，已读到的正文照常留在记录里。
- **provider 中途掉线**：正文已经流出去之后如果 provider 抛错（网关超时、524 等），后端不再把整条回复换成错误提示，而是把已收到的正文存下来并照常发 `done`，只丢掉选项与动作（`TownNpcTruncatedStreamIT`）。
- **超时分开配**：非流式用 `QWEN_TIMEOUT`，流式用 `QWEN_STREAM_TIMEOUT`（默认 PT130S，需与 `TOWN_CHAT_STREAM_TIMEOUT` 一致或更短）。
- **`response_format` 不是所有网关都支持**：某些 OpenAI 兼容网关收到 `{"type":"json_object"}` 会一直挂住直到 524，导致「每晚反思」「目标草案」这类结构化调用超时。这类网关把 `QWEN_JSON_MODE=false` 即可——schema 仍然写在 prompt 里，返回值走已有的去代码块 + 修复重试逻辑。

## 6. 位置连续性（在场坐标）

小镇里的人不能瞬移：刷新页面、切换设备、别人上线，看到的都应该是「他刚才在哪、正往哪走」，而不是按日程重新算出来的一个新落点。

### 6.1 数据

服务端为每个用户保存一份最近位置：

| 字段 | 说明 |
| --- | --- |
| `x` / `y` | 世界坐标（像素，小镇坐标系；室内场景各自坐标系） |
| `facing` | `up` / `down` / `left` / `right` |
| `scene` | `town`、`academy`、以及未来的室内房间 id |
| `updatedAt` | 服务端写入时间（UTC） |

### 6.2 上报

`POST /api/v1/town/presence`，请求体 `{ x, y, facing, scene }`。

- 客户端**节流**上报：停下来时报一次；移动中最多每 3 秒一次；页面隐藏或离开时报最后一次。
- 服务端做**速度校验**：与上一条记录比较，位移不得超过 `RUN_SPEED(264 px/s) × 间隔秒数 × 1.5` 的余量；超出则**夹到**允许的最大位移处并照常写入（而不是拒绝），避免网络抖动或长时间离线导致写入失败。跨 `scene` 时不做速度校验。
- 返回服务端最终采纳的 `{ x, y, facing, scene, updatedAt }`，客户端以返回值为准。

### 6.3 读取

`GET /api/v1/town` 的每个 resident 增加：

```json
"presence": { "x": 1234, "y": 832, "facing": "left", "scene": "town", "updatedAt": "...", "stale": false }
```

- `stale`：`updatedAt` 距今超过 10 分钟即为 `true`。
- 没有任何记录时 `presence` 为 `null`。

### 6.4 客户端连续性规则

1. **自己**：进入小镇时，若 `presence` 存在且 `scene` 匹配，就从该坐标出生；否则回到自家门口。
2. **别人**：轮询拿到新坐标后**不允许直接 setPosition**，一律设为行走目标，让小人自己走过去；距离过大（超过一屏）时才允许淡出淡入，并且要有明确的视觉过渡。
3. **stale 的居民**：按日程摆放，但仍然从上一次已知位置**走过去**，不瞬移。
4. 位置只用于呈现，不参与任何奖励计算；服务端的速度夹取只为防抖与防作弊，不作为惩罚。
