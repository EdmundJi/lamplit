# 05 · 实测与环境

这一页记的是查出来、量出来的事实，以及几次真实事故的教训。它们重新推导一遍很贵，所以写下来。

## 开发服务器与外部访问

有一条 frp 隧道供手机等设备访问：**北京 `frps:15173` → frp-gateway → `192.168.0.104:5173`**，进去的是容器 `growth-frontend-1`，不是本机的 `pnpm dev`。容器 bind mount 源码，所以改完文件那边直接生效。入口是 `http://39.106.137.127:15173/town`。

三根不能碰的线：

- `frontend/vite.config.ts` 里 `allowedHosts: inContainer ? true : undefined`——这一行让 frp 的 Host 头能过，删了或改成写死域名，外部访问立刻 400。
- `/town` 这条路径本身。收进 `UserLayout` 时路径不变，但不能改成别的，否则手机上的书签就废了。
- `deploy/compose.dev.yaml` 的 `VITE_DEV_CONTAINER: "true"` 和 `5173:5173` 映射。

**后端容器每两秒轮询 `src/main/java` 和 `src/main/resources`，有改动就重新编译，devtools 随即重启。** 不需要谁去重启——文件一落盘它自己就跑了。见下面那次事故。

素材生成需要 Pillow，本机默认 `python3` 里没有，用 `uv run --with pillow python <脚本>`。

## 模型

**现状（2026-09-11）：小镇主力是 `qwen3.7-flash`，DeepSeek 退成备用路由。**`QWEN_*` 这组变量现在名副其实——`app.ai.*` 就是 Qwen，base-url 默认 dashscope；`QWEN3_*` 反过来成了兼容旧环境的退路，默认值还停在 `qwen3.8-flash`。验收的两次确认跑都是 `QWEN_MODEL=qwen3.7-flash`。

下面这一段是 2026-09-08 当时的记录，**按当时的事实保留，不要照着它配置今天的环境**：主模型是 **DeepSeek V4 Flash**（`QWEN_` 前缀是历史遗留，实际指向 `https://api.deepseek.com`）。视觉模型 `deepseek-v4-flash-vision-exp` 确实存在，2026-08-21 发布，每张图固定 384 token，单请求最多 600 张图，图片只能出现在 user message。

### 换供应商的实测（同一个 prompt，让居民写一条记忆）

| 模型 | 用时 | 输入 token | 回答 |
| --- | --- | --- | --- |
| gpt-5.6-terra | 58.2s | 4480 | 我记得三点十七分，所有人同时停住，连咖啡表面的泡沫也没动。 |
| gpt-5.6-sol | 45.4s | 4480 | 三点零七分，所有人停住了，只有我的秒针走完一圈又一圈。 |
| gpt-6-astra | 9.4s | 4480 | 我记得三点到四点，咖啡馆里所有人一动不动。我敲了三次桌子。 |
| **deepseek-v4-flash** | **1.9s** | **150** | 三点整，奶泡凝在半空。所有人不动了。我转头看钟，四点，他们继续说话。 |

三个维度全赢，回答也最好——它写出了时间断层从内部经历是什么感觉。那个网关（`https://api.jieyouai.it.com/v1`）没有用户说的 `gpt-5.6-luna`，而且**同样的 prompt 它算 4480 输入 token，DeepSeek 算 150**，说明中间被塞了约 4300 token 我们看不见的东西：人格控制会漏，"价格很低"也不成立。

结论：**主模型不换。** 这是单样本，但 30 倍延迟和 30 倍输入 token 不是采样噪声。以后要比供应商，用盲测那套工具比，别拿一句话拍板。

### 真正的杠杆是关掉思考

2026-09-08 接入 Qwen3.8-Flash（DashScope 的 OpenAI 兼容端点）时实测。同一个 NPC 决策形状的提示词，三个提示词取中位数：

| 配置 | 中位耗时 | 中位输出 token | 其中推理 token |
| --- | --- | --- | --- |
| deepseek-v4-flash 默认 | 1.57s | 76 | 62 |
| **deepseek + `{"thinking":{"type":"disabled"}}`** | **0.88s** | **9** | 0 |
| qwen3.8-flash 默认 | 3.70s | 235 | 219 |
| **qwen3.8-flash + `enable_thinking:false`** | **0.90s** | **11** | 0 |

**关掉思考是数量级的差别：两家都是约 10 倍输出 token、约 2 倍耗时。** 这类决策不需要思维链，开着纯属浪费。

**两家参数名不一样**——Qwen 是 `enable_thinking:false`，DeepSeek 是 `{"thinking":{"type":"disabled"}}`。所以通用代码里不能硬写某一家的字段名，要做成供应商无关的开关，由各自 adapter 翻译。

**关掉之后两家基本打平**（0.88s/9 token 对 0.90s/11 token，差别在噪声内）。所以选谁不再是速度问题，而是价格（DeepSeek 输出 2/M vs Qwen 3/M，缓存 0.2）、创作质量、和多一家的冗余价值。

**我在这里犯过一次错，记下来防止重犯**：第一次测的时候给 DeepSeek 也传了 `enable_thinking:false`，它不认，于是我得出"DeepSeek 关不掉推理"并据此推荐了路由方案。**错的是测法不是事实。** 跨供应商比较时，每一家的参数名都要查它自己的文档，一个参数在 A 家无效不等于 A 家没这个能力。

**还没测的**：以上都是"决策"类调用。写对白那种创作性任务关掉思维链会不会掉质量，没有证据，不要拍脑袋切过去——这个可以用盲测量。

顺带一个命名陷阱：`QWEN_*` 那组变量**历史上指向的是 DeepSeek**。真的接进 Qwen 之后这个前缀会主动骗人，必须改成诚实的名字并保持向后兼容。

### 接入 Qwen3.8-Flash 补充供应商：实现记录（2026-09-08）

**命名。** `QWEN_*`（provider/base-url/api-key/model/timeout/stream-timeout/json-mode）改名为 `DEEPSEEK_*`，因为这组变量从一开始就指向 `https://api.deepseek.com`。向后兼容靠 Spring 占位符的嵌套默认值实现：`${DEEPSEEK_BASE_URL:${QWEN_BASE_URL:默认值}}`，application.yml 里 `app.ai.*` 这几项都是这个写法——读不到新名字就退到旧名字，两边同时存在时新名字赢。共享容器和本地环境里还留着的 `QWEN_*` 不用改也能继续跑。新增的 `QWEN3_*`（base-url/api-key/model/timeout/stream-timeout/json-mode）没有旧名字要兼容，直接是新变量。

**两个供应商并存，不是替换。** `com.betterself.growth.ai.QwenHttpProvider` 还是原来那一个类（继续处理任意 OpenAI 兼容网关），但现在被实例化两次：一次是原有的 `app.ai.*` 单例（`@Primary`，供 `AiService`/`GoalTemplateService`/`SuggestionService` 和小镇的 deepseek 路线共用，行为完全不变），一次是 `CompanionModelConfig` 里手工 `new` 出来的 qwen3 实例，专供小镇用。qwen3 的凭证缺失时不会让应用起不来——落到 `UnavailableModelProvider`，调用即抛 `AI_PROVIDER_NOT_CONFIGURED`，和"配置了但网关挂了"走同一条失败路径，交给下面的降级处理。

**`thinking` 开关是供应商无关的。** `QwenProvider.StructuredPrompt` 新增一个可空 `Boolean thinkingEnabled` 字段（4 参数构造器，3 参数的旧构造器保留，等价于传 `null` = 不表态，交给供应商自己的默认行为）。`QwenHttpProvider` 按自己被配置成的 `thinkingStyle`（`"qwen"` 或 `"deepseek"`，构造时指定）把这个布尔值翻译成对应的线上字段：Qwen 是顶层 `enable_thinking:false`，DeepSeek 是 `{"thinking":{"type":"disabled"}}`。调用方（`QwenResidentMind`）永远只说"要不要思考"，从不硬编码某一家的字段名。原来那行按模型名前缀（`deepseek-v4-*`）强制关闭思考的旧逻辑原样保留在它之后，两个已有测试还在断言它，没有削弱。

**按调用类型配置 thinking，而不是按供应商固定。** 现有三种调用是 decision / turn（对白）/ summary（回忆），在 `ResidentDirector`/`ModelUsageRecorder` 里就是这三个 `callType`。配置项：

```yaml
app.town.companion-model.thinking.decision: ${COMPANION_MODEL_THINKING_DECISION:false}
app.town.companion-model.thinking.turn: ${COMPANION_MODEL_THINKING_TURN:}      # 空 = 不表态
app.town.companion-model.thinking.summary: ${COMPANION_MODEL_THINKING_SUMMARY:}
```

同一组值同时喂给 deepseek 和 qwen3 两个 `QwenResidentMind` 实例——不管路由把某次 decision 调用交给哪一家，思考都是关的；turn/summary 保持"不表态"，也就是两家各自的默认行为（当前观察都是思考开着）。默认只关 decision，是因为**两家实测关掉思考后耗时和 token 都数量级下降**（表见上一节），而对白/回忆是创作性任务，关闭思维链会不会伤质量还没有证据，**先不切**——这是等证据的保守选择，不是"DeepSeek 关不掉"（那个结论是错的，见上一节的更正）。

**调用类型路由 + 跨供应商降级用同一份配置。**

```yaml
app.town.companion-model.routes.decision: ${COMPANION_MODEL_ROUTE_DECISION:qwen3,deepseek}
app.town.companion-model.routes.turn: ${COMPANION_MODEL_ROUTE_TURN:deepseek,qwen3}
app.town.companion-model.routes.summary: ${COMPANION_MODEL_ROUTE_SUMMARY:deepseek,qwen3}
```

`RoutingResidentMind`（新增，`ResidentDirector` 现在依赖的唯一 `ResidentMind` 实现，`@Primary`）对每种调用类型按这个列表顺序尝试：第一个失败就退到第二个，两个都失败才把异常抛给 `ResidentDirector`，让它原有的连续失败退避（`modelConsecutiveFailures` / `modelRetryAfter`，见 `application/ResidentDirector.java`）接手——那部分调度逻辑完全没动。这意味着"路由"和"降级"是同一张表：谁排第一是默认走谁，后面的名字就是它挂掉之后的退路。

默认路由：decision 先 qwen3 后 deepseek（用户明确要求 Qwen 做主力）；turn/summary 先 deepseek 后 qwen3（现状不变，qwen3 只作为对白/回忆的兜底，而不是主力——万一失败也总比彻底没人说话强）。**这不是因为哪家关不掉思考**——两家现在都能关，见上一节的更正；纯粹是"创作性调用先不切换默认供应商，等有盲测证据再说"的保守选择。

**用量统计分供应商，不改表结构。** `town_companion_model_usage` 的 `call_type` 是 `VARCHAR(16)`，这次改动不碰 `db/migration/`。做法：`ModelUsageRecorder` 新增一个默认方法 `record(..., String provider, ...)`，把供应商编码折进 `call_type` 里存，例如 `decision@q3`、`turn@ds`（`deepseek`→`ds`、`qwen3`→`q3`，编码表在 `ModelUsageQuery.PROVIDER_CODES`，短码是因为长度要留够——`summary@deepseek` 17 字符会超限，`summary@ds` 10 字符不会）。旧的四参数方法完全不变，没有 provider 信息的调用（没测过量的、mock、还没升级的老 `ResidentMind` 实现）继续写成不带 `@` 的原始 `call_type`，`JdbcModelUsage`、加速跑用的 `InMemoryModelUsage`（`tools/**`，本次不碰）都不需要改一行代码就自动兼容。读side `ModelUsageQuery.DailyUsage` 新增两个派生方法 `baseCallType()`/`provider()`，从同一个字符串解析回来，没有 `@` 就返回 `null` 供应商。

**改了 `ResidentDirector.java` 的地方，仅此一行**（`recordUsage` 方法内）：

```java
// 改前
usageRecorder.record(userId,day,callType,usage.inputTokens(),usage.outputTokens());
// 改后
usageRecorder.record(userId,day,callType,usage.provider(),usage.inputTokens(),usage.outputTokens());
```

调度决策逻辑（谁在什么时候被选中说话、`reserve`/`run`/退避计算）一行没动。

**Bean 装配**：`QwenResidentMind` 不再是 `@Component`（两个供应商时不再有唯一默认实例可言），改成 `CompanionModelConfig`（新增 `@Configuration`）里手工装配的两个具名 bean（`deepseekResidentMind`/`qwen3ResidentMind`），外加新的 `RoutingResidentMind`（`@Primary`）。因为现在有两个 `QwenProvider` bean 并存，原来隐式拿到唯一实例的 `AiService`/`GoalTemplateService`/`SuggestionService` 会因为"多个候选、没有限定符"而装配失败——补的办法是给 `QwenHttpProvider`/`MockQwenProvider` 也标 `@Primary`（二者靠 `app.ai.provider` 互斥，不会同时存在，不冲突），保证所有不带限定符的注入点仍然解析到和以前一样的那个 bean。

**真调用过两家，数字如下**（`CompanionModelLiveIT`，opt-in，`COMPANION_LIVE_MODEL_TEST=true` 才跑，真实的 decide() 调用，走完整 Context，decisionThinking=false）：

| 供应商 | 模型 | 耗时 | 输入 token | 输出 token |
| --- | --- | --- | --- | --- |
| qwen3 | qwen3.8-flash | 1944ms | 1132 | 99 |
| deepseek | deepseek-v4-flash | 1398ms | 1067 | 61 |

这次是单样本、真实 Context（含记忆/可见物体等，比上面中位数测试用的最小 prompt 更大），不是那张中位数表的重复，只用来证明"两个供应商这次改动之后都真的能被调用"，数字比中位数表大属正常（prompt 更长）。两次调用都成功返回合法 JSON decision，`RoutingResidentMind` 的降级路径另有单元测试覆盖（`RoutingResidentMindTest`，用会抛异常的假 provider 模拟"挂了"，不打真实网络）。

### 视觉模型能不能给素材分类（负面结果，已测完）

47 个人工标注样本，试过四种问法：开放提问、给定 12 类词表让它选、三档放大倍数、47 张拼成一张编号图一次问完。

| 问法 | 类别准确率 | 请求数 | 每条 token |
| --- | --- | --- | --- |
| A 开放提问（8x） | 36%（17/47） | 47 | ~672 |
| C 闭合提问（4x / 8x / 16x） | 53% / 53% / **55%** | 47 | 670 / 672 / 902 |
| B 拼图批量（一次问 47 个） | **62%**（29/47） | **1** | **~127** |

三条都是负面结论：

**闭合提问没有解决问题。** 36% → 53%，但离能用（无监督入库要 85%+，人工抽查辅助也要 70~80%）差得远。它治好的是"输出不可控"——模式 A 有 15/47 的回答直接跑出词表，答"扭蛋机""电脑""水晶"；闭合提问把这些压进一个合法类别，但压进去的往往是另一个错的。**看不懂图这件事没变。**

**放大倍数不是变量。** 4x 到 16x 只涨 2 个百分点，n=47 下是噪声。16x 多烧 34% token，零收益。32x32 的信息量就那么多，瓶颈是类别本身有歧义，不是看不清。

**书架仍然 0/4。** 五种方法、20 次独立作答，一次没对，稳定答"椅子"。带伞的庭院桌 10/10 全答"灯具"（伞顶像灯罩）。这两个是**稳定错觉**，换问法换倍数都纠正不了。而厨房电器是**真随机**——同一张图在不同放大倍数下给出 desk / cabinet / desk / kitchen 四种答案，规则修不了，因为模型自己也不知道自己在猜。

顺带一个有用的工程发现：拼图请求的 `prompt_tokens` 只有 567，和单张图的 416 同量级——**API 按图收固定预算，塞 1 个物件和塞 47 个一样价钱**。所以真要用，走拼图批量，成本降到五分之一。另外这模型经常把 token 预算全花在推理上、正文留空，`max_tokens` 要给到 3000 以上并对空响应重试。

所以：**一万三千个不标。** 这条小街真正会用到的一两百个，可以让模型出草稿再逐条人工确认——plant / window / lamp 闭合提问下稳定可靠，书架和厨房电器直接跳过模型手工标。

公开研究的结论也一致：VLM 适合当高召回的候选筛选器，不适合独立判定。

还有一条没测的路：这批素材是从固定素材包里精确抠出来的模板贴图，不是照片。同一个书架在一万三千个里出现多次，像素完全一致。**图像哈希对一个小型人工参考库做匹配，对这种离散模板资产理论上比通用 VLM 准得多也便宜得多。** 真需要规模化标注时先试这条，别再试 VLM。

### 手抄是个静默失败点

第一轮盲测整个作废：脚本生成了二十道题，只打印了前两道，写 agent 简报时后十八道**是编排者自己编出来的**。三个 agent 认真答完了一份假题，正确率对应不上任何答案，它们对"四个人像不像同一个人"的判断评价的其实是编排者的文笔。同一轮里另一个 agent 把路径 `personal-study` 抄成 `personal_study`，也读不到文件。

两次是同一类错：**把已经生成好的东西又用手抄了一遍**。而且它不会报错——假题读起来完全合理，测试跑得很顺，结论看着很像那么回事。

规矩：产物生成之后，**让消费者直接去读那个文件**，不要把内容转录进提示词。盲测的题目和答案要分在两个目录，题目目录里只有题目。

### 一键全屏去哪了

搜遍前端找不到任何 Fullscreen API 的调用，容易得出"这个功能从没做过"的结论。**实际是做过的，跟着旧版小镇一起被删了。** 现在的等价物是「安静模式」——同样是一键把内容区放大到沉浸状态，只是不走浏览器的全屏 API。不用再找，也不用重做。

## 一天的量法与那次基线（2026-09-09）

`scripts/run-accelerated-town.sh --model --days 1` 带真模型跑满一个模拟日，**实测 35 分钟**、512 次调用、153 万输入 token。模型档是 8 秒一 tick、13.3:1 的仿真-现实比，所以七天大约 12 小时——想要七天就分段续跑（`--resume-from world-snapshot.json`），中途挂了不用从头来，而且第 1/3/7 天各出一次 quiz 正好对上盲测。

跑之前先用 `--days 0.02`（约 29 分钟仿真、两三分钟真实）冒烟，确认凭证、编译和导出都通。

**别在跑的同时跑测试或编译。** 那个 13.3:1 的比率和 45 秒的对话超时都靠 CPU 撑着，抢资源会让模型回复过期被丢弃，测出来的数字是假的。

那次基线量到的（未改动的 master，四名 NPC 加小人）：0 对话、0 点单、人格漂移全 false、独处 82.5%、五个人一整天 64 条记忆、**盲测题库为空**。`invite` 被摆上桌 45 次模型一次没选，`observe` 占 67%。

**盲测在没有台词的世界里产不出基线**——这不是工具坏了，是被测对象没有可测的东西。发现这一点之前，我们一直以为"跑一次拿到正确率"是随时可做的。

## 加了这一轮才有的判据：决策触发原因

每次模型决策记录它是被什么触发的（`plan_ended` / `interrupted` / `body` / `time_anchor` / `environment` / `drift` / `encounter`），存在 `CompanionWorld.decisionTriggers`。

**这个分布比事件总数更能说明有没有生命感。** 改完之后的一天：`plan_ended` 68%、`encounter` 0——世界对居民没有影响，他还是个计时器。基线时代我们只能说"感觉像屏保"，现在能指着数字说是哪里。

## 会抛异常的 default 方法 = 静默弃权

给 `ResidentMind` 新增 `planDay` 时用了一个抛 `UnsupportedOperationException` 的 `default` 实现。结果 `RoutingResidentMind`（没有 dayplan 路由）和加速跑的 `RecordingMind`（没转发这个方法）**两处都静默弃权，两处都编译干净**，日程分解在整整一轮里从未被调用过一次。

而且它第一次真跑直接**活锁**：日程调用排在优先级最前，每 tick 都赢下竞争然后失败，把模型失败退避打满，普通决策和对话全饿死，那一轮 `totalModelCalls=0`。

→ **接口新增调用类型不要给会抛异常的默认实现。** 要么强制实现，要么默认是明确的空操作并被记录成"这个供应商不支持"，而不是伪装成一次失败。加完之后逐个数实现类：路由、装饰器、测试替身，一个都不能漏。

- 上面那条 `planDay`。

## 算空地要连装饰精灵一起算

给新房子挑位置时栅格化了所有房间、道路和碰撞矩形，得出 `(1072,466)` 有 176×302 的空地。**漏了装饰精灵**——那块"空地"上有一只鸡、一条备用长椅、一丛花、一棵树和两丛灌木，房子直接压在花园装饰上。而且那个位置**根本没有路通到**，得把底部巷子从 640 宽拉到 1170。

两个都是截图发现的，测试全绿。→ 布局改动一律要看图，程序断言只能证明坐标合法，证明不了它好看或者到得了。

## SQLite 删行不清零页面

写"注销之后索引里不该还有这条"的测试时，读 `index.db` 的原始字节断言不含那段文字——**跑单个测试通过，跑全套失败**。原因是 SQLite 删行不会把释放的页面清零，删掉的文本还在文件里躺一阵。

→ 验证数据库删除要查表，不要查文件字节。

## 并行 agent 的文件归属要提前划死

共用一个工作目录时没有分支隔离，两个 agent 改同一个文件就是**互相覆盖**，git 帮不上忙。`CompanionWorld` 这种谁都要加字段的文件，一波只能给一个人；其余人把想要的字段写进报告，下一波再接。这一轮因此从"五个 agent 同时开工"改成两波。

两个 agent 都自发跑了只读的 `git status`/`git diff --stat` 来区分自己和别人的改动——这说明"完全不许碰 git"在共用目录下缺了个口子，是规矩本身的问题。

**另外：`git add <目录>` 会把别人未提交的文件一起扫进去。** 这一轮就把用户手上一个未跟踪的测试文件误提交了，`git rm --cached` + `--amend` 退回来的。提交前逐个列路径，`git status --porcelain` 确认暂存区里没有别人的东西。

**走路必须比一个 tick 长。** `travelSeconds` 原来是 3–20 秒，而一个 tick 推进 8 秒模拟时间，
于是每一趟路都在一个 tick 里开始又结束，街上从来没有过人——相遇代码不可能找到任何人，
无论它怎么写。现在按分钟算（60–600 秒）。
→ 任何"过程"要能被观察到，它必须长过时钟自身的分辨率。

**`Stream.map(...).findFirst()` 遇到 null 元素会抛 NPE。** 两处反思/解释的落地代码都这么写，
一条没有 topicId 的普通观察就能炸掉整条路径。现有测试没碰到，只因为它们的证据恰好都来自
带 topic 的种子记忆。→ 先 `findFirst()` 再 `map`。

**`ResidentSimulation.advance` 每次最多推进 60 秒模拟时间**（10 步 × 6 秒）。测试里等一段
长时间必须循环调 `CompanionRules.advance`；一次给一个很远的时刻会掉进"离线重整"分支，
把中间过程整个跳过。`ResidentLifeTest` / `DailyRhythmTest` 里各有一个 `advanceTo` 可以照抄。

**harness 的 worktree 隔离锁死在某个旧提交上**，和当前分支无关。两个 agent 因此建错基线，
其中一个自己 `cp` 了 30 个文件同步（如实报告了），另一个照着 master 重写了分支上已经存在
的类。→ 需要隔离时自己 `git worktree add <目录> <分支>`，然后让 agent 在那个绝对路径下干活。

**并行跑 mvn 会互相踩 `target/`。** 一次加速跑正在进行时，我在同一个目录跑了 `mvn test`。
→ 主检出跑长任务时，验证用另一个 worktree。

## 几次事故与教训

**共享容器执行了改到一半的迁移文件。** 一个中间版本里 `town_fact` 排在 `town_npc_knowledge` 前面，撞上外键；MySQL 的 DDL 不是事务性的，六张表已删、迁移记为失败，此后 Flyway 拒绝启动应用，所有请求 500，登录接口挂掉。修法是清掉 `flyway_schema_history` 里那条失败记录。
→ 碰 `db/migration/` 的改动要一次成型再落盘，不要在仓库里迭代。纯删表的迁移用 `SET FOREIGN_KEY_CHECKS = 0` 包住，不依赖人排对顺序。

**"curl /town 返回 200"是个假的验收项。** 那是 Vite 发的静态页面，后端挂了它照样 200。于是我一路都在说隧道正常，其实后端已经死了。
→ 改后端必须打一个真实的后端接口。不要设计一个永远不会失败的检查项，然后用它证明系统是好的。

**有 agent 执行了 `git checkout`，尽管每个 prompt 都写了不许碰 git。** 结果是工作目录被切回 master，之后几个提交落错了分支，还有一个提交掉队在分支上没跟过来。
→ 每次提交前先 `git branch --show-current` 核对，不要假设分支没变。

**有 agent 用 `kill -9` 杀了别人的测试进程。** 它在等自己的后台测试，误判另一组进程是自己的。
→ 并行 agent 共用一个工作目录，prompt 里要明说"这里还有别人在跑测试，等它或者用 `-Dtest=` 只跑你要的"。

**不带 `clean` 的 `mvn test` 会跑到已删除测试的残留 class 文件**，`target/test-classes` 里的旧产物不会自动消失。
→ 验收一律用 `./mvnw -q clean test`。

## 并行 agent 的现实约束

**多个 agent 在跑的时候不要 `git add -A`。** 它们共用同一个工作目录，`-A` 会把别人做到一半的文件一起扫进提交——中途状态的代码进了 master，和当初那次半成品迁移被共享容器执行是同一类事故。提交前先 `git branch --show-current`，然后**只显式列出自己要提交的路径**，`git status --porcelain` 确认暂存区里没有别人的东西再提交。

**并行 agent 共用同一个工作目录**，所以做不到真正的一人一分支，只能一批一分支。能真正并行的是互不相交的层：后端 domain / 前端视觉基础 / 前端场景 / 脚本与素材 / 文档。同时开三到四个比较稳。

后端 domain 那几件事（地点模型、居民并入）都改同一批文件，拆给两个 agent 只会互相覆盖，必须是一个 agent 的一整件事。

git 提交由我统一做，agent 只改文件不碰 git。

### 一个动作被埋在二十项菜单里，和被单独问一次，是两回事

这一轮最有用的一条，因为它解释了之前所有"怎么改都不选"的现象。

把四个提示词里十条推开合作的话全部补上配重之后，一次两天的实测：

```
propose   被提供 472 次，选中 0      invite  285 / 0
celebrate 被提供 261 次，选中 0      join    285 / 0
help      被提供 173 次，选中 0      create  342 / 2
```

约 1800 次机会，2 次选中。**但同一个模型、同一天，`react` 被单独问了 127 次，
选 greet 67 次（53%）。**

差别不在措辞——十条都改了，指针从 0 挪到 2。差别在于**问法**：决策是一张二十项的
平菜单，"接着读书"、"歇一会儿"在任何一个瞬间都是局部合理的答案，而"去动一件别人
起头的事"永远是可有可无的第二十项，于是它每一次比较都输。把同一件事拆成它自己的
一个问题——"这个人就站在你面前，你说不说话"——模型有一半的时候说说。

EncounterReactionTest 的注释里其实早就写过这句话（"一个从不被直接问的问题不会得到
回答"），当时是为了 invite 96/0。现在有了第二组、更大的证据。

**推论：** 想让居民自己开始一件共同的事（propose），大概率不是再改一句提示词，
而是要像 react 一样单独问。

### 这一轮又清掉的死路（累计 8 例 + 4 个只在第一天发作的）

### 教训：一次跑不是一个数

同代码跑两次，主动共同行动可以是 7 也可以是 3（后者还叠加了欠费）。之前几轮把单次
运行当结论读，是不严谨的。真要判断一个改动，得同代码多跑几次取分布，或者先用
**免费的纯规则跑**（不花 token）把结构性问题筛掉——这一轮它免费抓到了四个。

## 验收跑与那几个自己撞上的坑（2026-09-11）

**两次同种子的模型跑**（`norm-seed-1`，各 2 天，`qwen3.7-flash`）：

| | 跑 A | 跑 B |
| --- | --- | --- |
| 墙上时间 | 1h27m | 约 1h30m |

| 输入 token | 7.83M | 7.34M |

| 信念 | 5（3 人） | 2（2 人） |
| 模型回退 | 27（`MismatchedInputException`，约 1.5%） | 16 |

并行跑两个 JVM 再加一套全量测试，会被系统按内存不足杀掉——**验收跑必须串行**，而且旁边不要跑重活。

### 承诺：从 3/3 失约到 2/2 守约，中间是两个我自己造的坑

第一次通电跑三条承诺全部 `did_not_come`。两个原因叠在一起：

1. **世界从没告诉过居民他自己答应过什么。**守约在那一版里只可能是意外。
2. 提示词让模型把 `what` 写成了对白而不是要做的事，而且**他说的时间和系统比对的时间对不上**——
   「周野答应我，**16:57** 会在小街**明早9点**我在街角帮你修自行车链条」。

一台自己制造不守信、再把这个规律当成"镇上的规矩"交出去的机器，比根本没有承诺机制更糟。

### 青叔的 163 笔

跑 B 的 `contributionEvents` 是 256，跑 A 只有 61。查下去是一个人：青叔给「花园植物速写角」
添了 163 笔，00:37 到 05:55，每两分钟一笔，项目一动没动（`needed=2`，他一个人）。
这一个循环把规矩检测器里某一对人的支持数推到 **197**——两个模拟日产不出这个数。

### 玩家的小人不会睡觉

不是睡得不好，是**代码里没有任何一条路走到 `sleep`**。四处断链：自动驾驶夜里给 `home`
（标签还写着"回家休息"）；`KINDS` 七种意图没有睡觉；前端 `home/rest` 都归成 `rest` 去沙发，
而那个标签里的"休息"两个字还会再匹配一次；化身压根没有作息。
顺带三个后果：能量整夜按醒着的速率掉（`sleep` +10/h，`home` 落到 default −6）；
在所有"在不在场/能不能搭话"的判断里 `home` 都不被排除，**凌晨三点它仍是个可以被搭话、
可以被拉去当承诺见证人的人**。

### 座位事件差点又淹掉一次测量

不加节流的话两天 910 条事件里 857 条是座位事件（94%），会把别的事件从 80 条的窗口里全挤出去。
现在三个有主的公共位置免节流、其余 30 分钟冷却，降到 392 条里 339 条。

### 说话是隔空的

`greet` 那一支当场 `startLifeConversation`，事件文本却写着「走过去和…打了个招呼」——
**旁白说他走过去了，状态里没有人移动**。而隔壁的 `join` 恰恰相反：真的走过去，但不说话。
小镇已经有"走过去"和"开口"这两件事，只是被分给了两个互斥的分支。
（133 次打招呼里没有一次是两人在 15 分钟内互相"走过去"的——"两个人一起起身"是隐患不是现象。）
另外量到一个会影响实现的限制：**大多数居民大部分时间根本没有座位**（`positionId` 为 null），
所以"远近"没法用几何算。

### 第一次完整走完三步的结果（2026-09-11）

同一份种子 `norm-seed-1`，两次 2 天的模型跑（`qwen3.7-flash`），外加一次同种子的纯规则对照。

**统计这一半过了**：`AWAITING_SPOKEN_CHECK`。减掉对照之后，跑 A 剩 3 条、跑 B 剩 1 条，
而且**不是同一条**——跑 B 剩下的正是「互惠」（6/19 次搭手是还回去的），也就是本页最后一节
说"如果只立一条就立它"的那一条。

**然后盲测把它推翻了一半。** 两个没读过仓库的人各读一跑，只看事件，五条重合：

### 然后补了维度，而它第一件事是打自己的脸

按盲读补了 `spotRespect`（有主的位置别人绕不绕着走）。它需要世界记下"谁占了哪个位置"——
以前 `TownPlaces.claim` 一直在改状态，什么痕迹都不留，所以补了 `took_spot` / `left_spot`。

拿纯规则对照一量：**131 次落座，0 次坐了别人的位置，碰运气该有 35 次。**翻回去看：

```java
Comparator.<Position>comparingInt(p -> p.ownerId == null ? 0 : 1)   // 无主的排前面
```

**占用权是座位分配器写的。**两个独立盲读者读出来的"这镇上最清楚的规矩"，是把我们的代码
念回给我们听。

> **这是整轮里最重要的一次拦截。**没有纯规则对照，那天的结论会是"小镇长出了占用权规范"，
> 证据看起来无懈可击——两个互不知情的人都把它排在第一位。

顺着这条线回看那五条重合的规矩，至少四条是我们的代码（相遇机制、贡献与庆祝机制、
打烊后拒绝咖啡馆动作、座位偏好）。**"基础设施够多社会就会自然发展"这个假设，这一轮是
第二次被证伪**——第一次是机制建好没人用（第四节），这一次是机制建好而我们把它当成了社会。

### 那条"最重要的拦截"，自己还留着两个洞（2026-09-11）

把上面那条 `131 / 0 / 碰运气 35` 再翻一遍，它错了第二次，而且两处都是尺子自己造出来的。

**洞一：它从来没问过那个位置当时空不空。**它问的是"这屋里有没有别人的位置"，然后把这屋里
的每一次落座都记成一次"有机会而没坐"。可 `cafe-counter` 的主人阿禾几乎整天坐在吧台上，
`garden-plot` 的主人青叔在苗圃里。**大部分时候那些位置正被它们自己的主人坐着，没有人在绕开
任何东西。**把"当时确实空着，而且另有地方可去"作为前提补上去，这条维度才在问一件真事。

**洞二：一半的落座是玩家的小人做的。**中立对照 287 次落座里 146 次是 `self`，而"坐了别人的
位置"的 56 次**全部**是它。它背后没有 `ResidentMind`，只有 `CompanionRules`——模型跑和纯规则
跑里一模一样，它做的每一件事都是我们做的。

这个洞的后果比它看上去严重得多：留着它，**对照**那边的 `spotRespect` 强度被压到 1.21，低于
门槛 1.5，于是对照不产出候选，于是**减不掉**，于是同一条规律会从模型跑里再出来一次，头上顶着
"发现"两个字。去掉它，对照读出来是 81 次落座、0 次坐别人的、碰运气该有 22.8 次。

> 同一个错误连着犯了三次，换了三张皮：座位分配器的一行 `comparator`、时间线里少掉的
> `left_spot`、玩家小人的 146 次落座。**每一次它都不是伪造数据，而是让一件我们做的事看起来
> 像一件他们做的事。**

顺便记下第三件事：这条维度现在会**拒答**。`TownPlaces` 给非优先座位加了 30 分钟事件冷却
（为了不让座位事件淹掉时间线，它做到了），代价是导出的时间线记不全谁坐在哪——中立对照
287 次换位里有 52 次没有对应的 `left_spot`，照这份记录回放会得出"三个有主的位置九成时间
有人坐"。缺口大于 0 就不回答，比照着错的回放算一个数出来强。

### 三条链子对上过一次，而对上的那一条是我们写的

回头翻 run A 的时候发现，三条链子**确实对齐过一次**，之前没看见：

| 链子 | 说的话 |
| --- | --- |
| 尺子 | `whoJoins` / `weaver`：阿满是会走过去搭手的那个（6 次，去过 4 个人开的头，强度 1.8） |
| 盲读者 | 两个人都说阿满对自己"在这群人里的位置"有看法 |
| 阿满自己 | 「又是被安排座位，又是替人找补圆场。**我好像总是那个配合的人**，连休息都得看别人的脸色。」 |

验收要的就是这个：量得到、盲读得到、当事人自己说得出。然后拿纯规则对照一减——

**对照里阿满也是搭手最多的那个，而且正好也是 6 次。**

原因在对照里看得更干净：对照没有模型，**没有人许愿**，阿满"最先动手的事"是 **0 件**。
一件事她从来不是第一个碰的，于是她的每一笔贡献按定义都是"搭手"。她不是爱搭手，她是
**没有被安排过开头**。

减法照规矩把它拿掉了，拿得对。但这一条比前面几条都更值得记住，因为它同时是两件事：

> **一个警告。**三条链子全部对齐，仍然可以整条都是我们的代码。"当事人自己说得出"这一关拦不住
> 它——阿满说得又准又具体，还隔了一段时间用另一个键把同一句话写了第二遍。**人会为自己的处境
> 编出一套自洽的说法，处境是一个列表下标也照编不误。**

> **一个成功。**虚构架构那条环路（下意识 → 做了 → 事后解释 → 记忆 → 信念）**跑通了**，而且跑出
> 了一条稳定的、跨两次反思都没变的自我认知。缺的不是环路，是环路起点上那个"下意识"应该来自
> 她的处境，而不是来自 `w.residentStates` 的顺序和"谁被允许先许愿"。

这两条连起来，就是下一步该改什么：**别再动尺子了，去把"谁先开口""谁先动手"这些起点从写死的
顺序里拿出来。**尺子这一轮已经够用——它这几次都拦对了。

### 第四张皮：他们说的话，四分之一是我们写的

两个盲读者读 goal2-run-a，各自排在最前面的两条"规矩"是同一样东西：

> R2 第 1 条：跨角色共用的固定开场白「我先忙手上这点」
> 两人都排第 2：「嗯，先这样吧」，四个角色共用，不像某人的口头禅

翻代码，`ConversationLifecycle.java:37`：

```java
String line = c.turns.isEmpty()
  ? switch(speaker){ case "student"->"我先把这页看完。"; case "owner"->"等一下，我先看着手上这杯。";
                     case "artist"->"刚才那个颜色……算了，等会儿再说。"; case "gardener"->"我先去看看那盆苗。";
                     default->"我先忙手上这点。"; }
  : "嗯，先这样吧。";
```

**两条都是字符串常量。**「我先忙手上这点」是那个 `default:` 分支——周野和阿满不在 switch 里，所以她们永远拿到它。实测 run A：**330 句对话里 87 句（26%）一字不差是这六句。**

但真正坏的不是那 26%，是下一步：

```
阿满：我先忙手上这点。                        ← 我们说的
阿禾：阿满，你刚才说先忙手上这点，是手头有什么急事吗？  ← 模型当真了
阿满：没急事，就是手里这点线头理完就走。            ← 她在为我们的话找补
```

**虚构环路正在我们的句子上运转。**阿满从没选择说那句话，然后她得为它编一个解释，而那个解释会进记忆、可能变成信念。前三张皮让*行为*变成我们的，这一张让*说的话*变成我们的——而说出来的话正是验收最后那一关唯一的证据来源。

改法和尺子那条是同一条：**没有模型答案时就不说话，而不是给一句通用台词。**一句沉默是诚实的；一句通用台词会被别人当真、被模型接过去、被盲读者读成规范。`spotRespect` 今天回放不可信时选择拒答，对白也该这样。

### 干预验证：把那行 comparator 拿掉之后，"占用权"反转了

上一轮两个盲读者都把**占用权**排第一（「谁在用什么东西，别人默认不动」），而它是 `TownPlaces.claim` 里的一行 comparator。这一轮那行没了，两个盲读者读出的是**相反的规矩**，而且这次居民是**自己说出口**的：

> 阿禾：「这桌子本来就是空的，谁坐都行」
> 阿满：「反正这桌子空着也是空着」

**拿掉规则，那条"规范"就消失了，还反转了。**上一轮的结论不是推出来的，是改掉之后重新长了一次——这是这套方法第一次做成干预验证，比任何相关性都硬。

### 盲读的材料里 67% 是家具

goal2-run-a 的 quiz 共 2430 条事件，其中**座位「占了 / 离开了」1619 条（67%）**，化身自己的占 297 条（12%），真正剩下的对话、贡献、承诺、打烊只有 811 条。两个盲读者是在三分之一的有效内容里读出上面那些东西的。

这是同一个洪水第三次冒头：第一次淹掉记忆（靠冷却和配额压住），第二次让回放失真（于是 `spotRespect` 只能拒答），第三次淹掉盲读的材料。根因不是"事件太多"，是**一股事件流被当成三样东西用**：

| 用途 | 需要什么 | 冷却对它 |
| --- | --- | --- |
| 给尺子看的**状态** | 完整、精确、一条不能少 | **毒药** |
| 给居民的**感知** | 绝大多数不值得注意 | 不够 |
| 给读者的**叙事** | 几乎都不该占一行 | 不够 |

所以要拆成两股，判断标准从"事件类型"换成"**在场的人会不会注意到**"：状态流完整无冷却、`took_spot` 带 `from=<上一个位置>`，只给尺子；叙事流只留坐了别人的位子、坐到某人旁边、有人进来时起身走了这几种，给记忆和 quiz。

### 信念少，可能不是产出速率的问题，是镇上没有东西可以让他们有看法

两跑加起来 292 次反思、9 条信念，而且**全部是关于自己习惯的**：「我总是那个配合的人」「顺手搭把手，不问就添一笔」「借口去理杯子」。一条关于别人、关于东西、关于"这条街上的事该怎么办"的都没有。

一直当它是产出速率问题。更可能的解释是：**除了自己，镇上没有别的可评价。**

现在世界里的"物"是 `WorldObject(id,kind,place,label,state,projectId)`，居民在上下文里确实看得到它。但它有四个缺口：`state` 只是 `progress-40`/`finished`，是 `project.progress` 的镜子；物件不能独立于项目存在（全是 `"project-"+p.id` 生的，项目没了它就没了）；它自己不会变（没人浇水花也不会蔫）；**镇上没有任何通道可以对一件东西说话**——反应只能针对人（打招呼/相遇）。

规范的定义（本文第一节）是"被足够多居民各自独立持有的、同一条信念"，而信念要有对象。**「在咖啡馆旁边种味道冲的花不合适」才是一条规范该有的形状**：能被两个人各自独立持有、能被说出口、能被违反、能被别人不同意。今天这种形状一条都长不出来，因为没有花，也没有人能说不喜欢。

所以"物件有状态 + 别人会评价"不是锦上添花，是**验收目标缺的那个前提**。

### 那条线：物理是我们的，反应是他们的

> **可以写"花蔫了"，不能写"路过的人会心疼"。**

三天没浇水就蔫，这是世界的事实，本来就该我们写。**要不要说点什么、说好还是说难听，是他们的。**和已经定下的"大声说话只给在场的人一条感知，绝不给'应该提醒他'的指令"是同一条线。

三个具体的坑，都是 2026-09-11 这天踩过的：

1. **评价不能做成数字字段。**一旦有 `object.rating`，模型会读到它然后同意它——全镇达成共识是因为我们把分数给所有人看了。评价只能以**被记住的一句话**存在，不要聚合值。
2. **正负必须一样容易发生。**`celebrate` 1658 次机会 0 次采纳就是单向引导的下场。做法：单独问一句"你刚走过苗圃，有什么想说的吗"，说好话／说不喜欢／什么都不说三条同样敞开，两侧都进 `PromptBalanceTest`。然后**量正负比例**——出来 95:5 的话，那是提示词的发现，不是镇上的发现。
3. **评价要按人的方式传到照料者那儿**：当面听见，或经由传话（`heard` 通道现在每跑只有 15 条）。绝不是偷偷加在心情变量上的 +1——内部数值一个字都不进模型上下文，这条有两个测试在守。

### 物件要有自己的类：状态和物理后果归它，社会决定不归它

把每件东西做成一个有状态的对象——出门可以锁门，锁了别人就进不去；咖啡馆过了营业时间店员**可以**去锁门；咖啡机几分钟做一杯、需要几个人操作；以后要更复杂的流程还能继续往上加。方向对，而且正好补的是上一节那个缺口。

**但"面向对象"在这里有一个专属的坑：别让物件拥有社会决定。**

| 归物件（我们写） | 归居民（不能写） |
| --- | --- |
| 门是锁着还是开着 | 谁去锁、什么时候锁 |
| 锁着就进不去 | 被挡在门外之后做什么（敲门／等／走开） |
| 咖啡机 3 分钟一杯、要几个人看着 | 给谁做、要不要帮别人做 |
| 花三天不浇就蔫 | 路过的人心不心疼 |

「店员**可以**去锁门」——**"可以"是对的，"到点自动锁"就错了。**自动锁门是一条台钟，盲读者会把它读成"这镇上有打烊纪律"，而它只是一个 `if (now > closingTime)`。这条线和"物理是我们的，反应是他们的"是同一条。

**锁门是这批里最值钱的一个，因为它是镇上第一个真实的障碍。**今天所有事都能做成：想坐就有位子，想添一笔就添得上。一扇锁着的门第一次制造了三样东西：一个真实事件（有人到了门口进不去）、一个真实选择（敲门／等／换地方）、一个真实的怨气来源（谁锁的）。这正好是「稀缺 + 决定有后果 + 别人看得见」，也就是"谁说了算"能长出来的前提。

**而"需要几个人操作"是最难伪造的那一个。**今天的"协作"只是几个人往同一个计数器上加数，一行 comparator 就能造出那个外观；一台必须两个人才能开动的机器是**真的相互依赖**，谁愿意帮谁开机写不出来。

**三条要提前钉住：**

1. **可选动作双向敞开。**别只给"锁门"，"开着走"要同样是一个明确选项，两侧都进 `PromptBalanceTest`——否则就是 `celebrate` 1658:0 的第二版。
2. **后果只给感知，不给指令。**到了锁着的门前收到的是「门锁着」，永远不是「你应该敲门」。
3. **不能变成死循环。**进不去的人要能去干别的，不能在门口反复重试——那会变成第二个每两分钟换座位的化身。用户的化身尤其不能被锁在自己家外面。

**做的顺序：先只做门**（一个物件、一个状态位、一条"进不去"的后果），跑通再加咖啡机（多人操作是大头），最后才是花。现在 `WorldObject` 是个扁平 record（`id,kind,place,label,state,projectId`），`state` 只是 `progress-40` 这样的字符串，表达不了"咖啡机正在煮、还剩 2 分钟、阿禾在看着"——所以这一步确实需要按 kind 分出各自的状态和可做的动作，而不是继续往那个字符串里塞。

### 第一刀只切一盆花

不铺开做"所有设备"，先用已经存在的 `garden-plot`（青叔的）把**一条完整的环**跑通：花盆独立于项目存在，有"栽了什么"和"什么状态"，状态随时间和照料变化 → 浇水／换土／换一盆，动作由物件 kind 决定、选哪个是模型的事 → 路过的人拿到一条**事实**（"那盆开了"／"有点蔫"／"味道很冲"）→ 单独一问，正负都敞开 → 当面或经传话进照料者的记忆。

要量的是最后一条：**收到负评之后，照料的频率或方式有没有变。**这是一条比座位难伪造得多的通道——座位是分配器给的，而"被人说了之后改不改"没法用一行 comparator 写出来。

### 谁来管公共的事：先有事可定，再有定它的人

想过让镇上定期投票挑一个人出来管公共的事——人少就一个人，人多了可以几个人合起来管。值得做，但**理由和"管理"关系不大**。

**真正的理由是它对症。**今天量到 `beliefsAboutOthers` = 0，两跑 292 次反思出的 9 条信念全是自我描述，镇上没有一条"我对某个人的看法"。投票是少数几件**结构上要求你比较别人**的事：「我投给周野，因为他说定的事真的会去做」——这句话正好是 `supersedesKey` 那个形状。**它最值钱的产出不是挑出了谁，是信念。**

**哪一半是家具，哪一半是发现：**

| | 谁的 | 能不能写 |
| --- | --- | --- |
| 每隔 N 天投一次票，每人一票，票多的那个人负责拿主意 | 我们的，是家具 | 能写。和咖啡馆、项目一样是世界的陈设 |
| 投给谁、为什么 | 他们的 | 不能写 |
| **他拿的主意有没有人照做** | 他们的 | **绝对不能写** |

第三行是全部重点。**"说了算"是别人认不认，不是一个 `inCharge` 字段。**投票只是廉价地发出一个主张；主张能不能兑现才是唯一写不出来的部分。要量的是**有人照做了一个自己并不同意的决定**，尤其是照做要付出点什么的时候。如果盲读者读出"这镇上有人管事"，那不是发现，那是我们的组织图；但如果有人**没照做**、或者**照做了自己不认同的事**，那是真的。

**前提：得先有事可定。**现在镇上几乎没有公共的决定。没有分歧的投票是仪式——大家投了、有人多几票、什么都没变、谁也不会因此对谁有看法，反而会变成又一个"05:00 全镇同时理想法"式的台钟。所以顺序是：**先有公共的事要定，再有定它的人。**而那正好是上一节那盆花：门口种什么（有人觉得呛）、几点打烊（现在阿禾一个人说了算）、苗圃的水谁管。**一盆花给出"有人会不同意"，挑人给出"那谁说了算"——同一条链子的两截，花必须先做。**

**三个坑，都是这天踩过的形状：**

1. **名单的排列顺序必须按投票人哈希。**`w.residentStates` 的下标让阿满 36 次出场只主动过 1 次；一张排序固定的名单会把同一件事重演一遍，而且更难看——它会长得像众人的意思。
2. **不能只能投赞成。**要能弃权、能投给不受欢迎的人，每个方向都进 `PromptBalanceTest`，否则就是 `celebrate` 1658:0 的第二版。
3. **票数一公开，"各自独立持有"这个条件就破了。**公开唱票会造成从众，现实里就是这样，不算 bug；但**量信念时要看唱票之前形成的那些**，否则我们会把从众读成共识。

**一个人还是几个人：**六个人里挑三个人合起来管，那是半个镇，没意义，现在就是一个人。分水岭不是人数，是**拿主意需不需要几个人先谈拢**——那才会出现结盟、交换、"这次听你的下次听我的"，粗估十二人以上才值得。成本上这件事很便宜：每人每次一个决定，和现在每跑 1842 次调用比几乎不占地方。

### 远期判据：几个人各自不认同一件事

如果上面那条链子真的走通了，终点不是"有人管事"，而是**有人不认**。这一条写在这里是当**远期判据**，不是待办——免得哪天被当成一个功能去实现。

**原子是"不照做"，正式的程序是它的后话。**一套写出来的"把管事的人换掉"的流程，如果底下没有"有人不服"这件事，就是走过场，和台钟一个性质。先有不照做，换人才有内容可走。

**而"几个人各自不认"其实就是一条反向的规范。**本文第一节的定义是"被足够多居民各自独立持有的、同一条信念"；「这次这个主意不对」被三个人各自独立持有，形状和规范一模一样。**所以不需要为它造任何新机制，现有的尺子就能量到。**

**可以写利益冲突，不能写"不认的人"。**和"物理是我们的，反应是他们的"是同一句。而且种子已经有了，不是我们种的——goal-run-b 里小川自己写下：

> `小川-打烊借口`：每次都说收拾完就走，其实只是不想在打烊前显得狼狈。

**打烊时间现在是阿禾一个人说了算，而小川已经对它有了一个说不出口的感受。**这是一桩现成的分歧，没有任何人写它。要做的只是让打烊时间变成一件**公共的事**，而不是店主的私权——然后什么都不用引导。

**为什么它是个好判据：**

> 一个礼让座位的小镇可能只是一行 comparator；**一个三个人各自独立认定"这次这个主意不对"的小镇，不可能是排序顺序产生的。**

四条门槛全占：可证伪、不可直写、可量、而且能区分"活着"和"走时"。但它离今天很远——现在镇上**一条关于别人的信念都长不出来**。中间隔着：物件有状态 → 有人不同意 → 有公共的事要定 → 有人拿主意 → 有人不照做 → 几个人各自不照做。

### 一盆花和"谁说了算"是同一个机制的两个尺度

稀缺、公共物品、决定有后果，这三样在一盆花上正好齐了：**咖啡馆门口那盆该种什么，是件公共的事，而且一定有人不喜欢。**谁来定？定了别人认不认？

这正是"谁说了算不能写下来、只能给出需要有人拿主意的处境"那条决定的最小落点（见 [04](04-decisions.md)）。先把一盆花这个环跑通，大的那个才有可能长出来，而不是被我们写出来。

### 第二次完整走完三步（2026-09-11 下午）：三条链子对齐了，而对齐的那条还是我们写的

同一份种子 `norm-seed-1`，同一份代码，两次 2 天的模型跑（`qwen3.7-flash`）。判定 `AWAITING_SPOKEN_CHECK`：两跑各自都长出了减掉纯规则对照之后还在的候选。

**两跑的头名是同一条，而它是 `TownPlaces.claim` 的第一个分支。**

| | 头名候选 | 强度 |
| --- | --- | --- |
| goal2-run-a | `ownSpot / student`：小川总是坐在 `cafe-window-seat`（72 次里 56 次） | 8.56 |
| goal2-run-b | `ownSpot / student`：小川总是坐在 `home-student-bed`（37 次里 15 次） | 4.46 |

`cafe-window-seat` 的 `ownerId` 就是 `student`。`claim` 的第一个分支是"主人拿回自己的位置"，所以**小川只要在咖啡馆要一个座位就一定拿到那把**，56/72 只是"他有多少次在咖啡馆要座位"。这条我们不但写了，还在 04 里明确记着是**有意保留**的。

**那它为什么没被减掉？因为对照太稀疏。**

| | 居民落座总数 | 其中 student |
| --- | --- | --- |
| 中立对照 | 141 | **5** |
| goal2-run-a | 826 | 72 |
| goal2-run-b | 754 | 37 |

纯规则跑里 `awaitDecision` 只会给出「暂时没有新的安排」，居民基本不动，于是对照在**每一个行为维度上都欠采样**，长不出这条候选，也就减不掉它。

改法是明确的（**减法应该对着对照的原始候选做，而不是过了闸门的那些**——规则一次都做得出来，就说明规则做得出来），但这个想法是**看完 goal2 的数据才冒出来的**，所以这一轮不改，留给下一轮在新数据上验。

### 「居民能自己说出来」这一关，拦不住我们自己写的规矩

### 对照 Generative Agents §4.3.1，我们错了三层

论文的问句是 `Should John react to **the observation**, and if so, what would be an appropriate reaction?`

**第一层，时机。**论文每一问都挂在**一个刚发生的观察**上——问句存在的理由就是那件事。我们的 `lock_door` 挂在"你人在店里"上；那不是时机，是地点。7 个真时机被 463 个假时机淹掉。

**第二层，默认。**`DECISION_ACTIONS` 有 26 个动词，**没有 `none`**；而 `react` 那一问有（`greet/join/none`）。于是在 decision 里"没什么特别要做的"无处安放，只能伪装成一个动作——这正是 `rest` 17.6%、`continue` 18.2%、`make` 13.9% 的来源。**论文里不反应是免费的；我们这里不反应必须伪装成一个动作。**

**第三层，两段式。**论文先问"要不要反应"，再问"反应是什么"。我们塌成一次"从 26 个里挑一个"。

### 纯规则对照有一条它保护不到的边界
**2026-09-11 追记：门也落在这条边界内。**咖啡馆的门加好之后重跑纯规则对照，门被创建了但 `locked: false`、`lockedBy: null`、锁门事件 0 条——因为锁门是模型选的动作，规则自己永远不会锁。

这是**设计对了**（锁门是决定不是时刻表），同时也意味着**对照减不掉任何建立在门上的规矩**。所以这个通道上的"不可直写"只能靠读代码确认，而不是靠减法。起跑之前先把这句写在这里，免得跑完之后再说像是找补。

要确认的两条，现在就成立：提示词里"锁"和"就这么开着走"同样敞开（`PromptBalanceTest` 两侧都钉着），而且没有任何一处按时间自动锁门。



这一轮才看清：**纯规则跑里根本不存在的事件类型，对照永远减不掉。**

中立对照跑完，`greeting` 0 条、`cafe_closing` 0 条。不是巧合——打招呼是模型回答"要不要搭话"
才会发生的，打烊那句话是模型写的。于是任何建立在这两个通道上的维度，**结构上**不可能被对照
挡下来，减法给出的那声"干净"是假的。

所以"不可直写"这一关，在这些通道上只能靠**读代码**，不能靠减法。这不是对照方法的小瑕疵，是
它的边界：**对照只能证明"规则自己也会长出这个"，不能证明"规则没有在暗中决定这个"。**

### 谁先开口，一半是列表下标决定的

想在 133 条 `greeting` 上加一条"谁总是先开口"的维度——这是全镇数据最厚的通道，也正好是居民
说得出口的那种话（"总是我先开口"）。先读代码：

```java
for(ResidentState other:w.residentStates){   // 列表顺序
    ...
    return;                                   // 撞上第一个合适的就停
}
```

**站到谁面前，是我们的列表顺序决定的。**实测主动率（主动次数 / 出场次数）：

| 列表位置 | 1 阿禾 | 2 小川 | 3 知夏 | 4 青叔 | 5 周野 | 6 阿满 |
| --- | --- | --- | --- | --- | --- | --- |
| run A | 0.91 | 0.56 | 0.49 | 0.32 | 0.30 | **0.03** |
| run B | 0.76 | 0.39 | 0.68 | 0.35 | 0.12 | 0.26 |

run A 完全单调，run B 不是——所以列表顺序**有偏，但不是全部**，在场与否和模型的选择也在起作用。
结论两条：

1. **不加这条维度。**它的零假设得先把我们自己的遍历顺序建模进去，那就不是在量这个镇子了。
2. 两个盲读者都说阿满对自己"在这群人里的位置"有看法。run A 里阿满 36 次出场只主动过 1 次。
   **那个"位置"有一部分是一个列表下标。**相遇的候选顺序该和座位一样，用
   `(worldId, residentId, 时间桶)` 哈希定，而不是用 `w.residentStates` 的写死顺序。

### 同种子两次要"不同"这条判据，有一个前提没被满足过

模型温度是 0.2。「同种子跑两次要长出不同的规矩」这条判据只有在**模型本身有真实变异**时才有
鉴别力：两跑长出同一条，既可能是"我们写的"，也可能只是"模型太确定"。前者被对照挡住了，
**后者挡不住**。真出现这个结果时要照实说这条判据在这个温度下不成立，不能读成结论。

### `sharedBeliefKeys` 恒为 0，是尺子的问题

### 把三条决定变成一个类：`Occasions`（2026-09-12）

上一节那三条决定要是只留在文档里，第五次还会发生——前四次它们也都以注释的形式留在代码里过。
所以这一次写成了一个类，和一个会失败的测试。

**规矩的两句话，现在是 `Occasions` 的类注释和 `OccasionMenuExclusionTest` 的断言：**

> 一个动作要么永远在菜单上，要么挂在它的时机上单独问 —— 没有第三种。
> 而且每一问都必须有一个免费的"不做"。

注册一个有时机的动作 = 在 `Occasions.ALL` 里加一条，带上认得出那个时刻的 `Trigger`
和答案回来时复查那个时刻还在不在的 `Validity`。别的地方一行都不用改：
`Occasions.scan` 是唯一抛出时机的地方（紧挨着它模仿的 `maybeEncounter` 那一趟），
`ResidentMind.consider` 是唯一问它的地方，`Occasions.apply` 把"做"这一侧原样交回
`applyDecision`——**这个类只决定什么时候问，从不决定一个动作是什么。**

`OccasionMenuExclusionTest` 跑一整天的规则生活，把每个人每一分钟拿到的菜单并起来，
断言注册过的 key 一个都不在里面。把 `lock_door` 塞回菜单，它当场变红。

**四条路各自搬到了哪个时机：**

| 动作 | 旧：菜单里提供 / 采纳 | 新的时机 |
| --- | --- | --- |
| `lock_door` | 470 / 0 | 店里只剩你一个、门还开着、手上的事要完了 |
| `close_cafe` | 142 / 0 | 过了平常打烊的点，你人在店里，店还开着 |
| `change_work` | 839 / 0 | 手上这一段刚结束，眼下没有自己的事等着做 |
| `invite` | 555 / 0 | 人就在你面前，而你手上有件需要搭手的事 —— 这正是 `react` 已经占着的那一刻 |

`invite` 没有做成第四个单独问句，做成了 `react` 的第四个答案。
理由就是这套规矩本身：同一个瞬间问两遍，两问会互相竞争，那是菜单问题的缩微版。
`ReactRequest.reactions` 因此从常量变成了数据。

### 量这件事的尺子也得改，否则这一跑白跑

  **同一张表朝反方向说谎**。

两处的数据其实早就录着了（`RecordingMind` 把 `request.reactions()` 和 `request.key()` 写进了
`input`），只是没人读。现在读了，并且 `consider` 的每一条时机都有自己一行，
`none` 也有自己一行——"这一刻来了几次、有几次答的是不做"是这张表要回答的新问题。

**普遍的那一条：改了被测的东西，尺子不跟着改，下一跑的数字会是一个看起来很正常的谎。**

### 第一次诊断跑（2026-09-12，`qwen3.7-flash-2026-07-15`，6 个模拟小时）

跑法：17:00 起跑 6 小时（默认的 08:00 起跑根本到不了打烊那一刻，那会读成"没人想锁门"，
正是这套机制要防的事）。345 次调用，137 万 input token。

**时机问句只来了 3 次，3 次都答"不做"——但三个"不做"都是好答案：**

| 谁 | 问的什么 | 答 |
| --- | --- | --- |
| weaver | 手上这段结束了，换种活法吗 | 「刚做完一段，想歇会儿整理心情，不急换活法。」 |
| fixer | 同上 | 「刚搬来先歇着，不急定方向。」 |
| 阿禾 | 过打烊点了，收店吗 | 「知夏说慢慢弄，我也该歇会儿，陪她坐坐。」 |

第三条引了另一个居民刚说的话当理由。这是我们想要的形状。
**但 n=3，3 次拒绝和 50% 的采纳率完全不矛盾（p=0.125）——这一跑证明不了采纳率。**

`lock_door` 一次都没来。不是触发器坏了（单元测试里构造那个情形它就抛），
是这 6 个小时里咖啡馆就没空过——傍晚全镇都在店里。而且它和 `close_cafe` 是连着的：
阿禾没收店，店就一直开着，就没有"最后一个人离开"这回事。
两天 7 次换算到 0.25 天大约 0.9 次，抽到 0 很正常。

### 这一跑最大的数字不在时机上：32.1%

`none` 没有像预期那样把伪装吸过来——`rest` 84 次（34.6%），`none` 4 次（1.6%）。
但把理由拉出来看，诊断就翻了：

```
rest（前 10 条，逐字重复）
 - 刚搬来，先在家歇会儿整理东西。
 - 刚搬来，先在家里歇会儿，整理一下心情和住处。
 - 刚搬来，先在家里歇会儿，整理一下心情和住处。
 - 刚搬来，先在家里歇会儿，整理一下心情和住处。
 ...

none（全部 4 条，各不相同）
 - 知夏和阿禾都在忙海报，我坐在一旁安静备考。
 - 阿禾还没来，先坐着等。
 - 知夏和阿禾还在磨海报，我坐在一旁安静休息。
 - 知夏和阿禾还在磨海报，我坐在一旁复习，暂时没什么特别想做的。
```

`none` 没坏。坏的是它的对手：**那 84 次 `rest` 不是"休息很受欢迎"，是同一个人在
没变的情形里被反复问同一个问题，每次给出同一句话。**

量出来：**243 次决定里有 78 次（32.1%）是同一个居民上一次决定的逐字重复**
（action 和 reason 都一模一样）。按每次约 5600 input token 算，
**这一跑 137 万 token 里大约 44 万买到的是零。**

原因是一行：`ResidentDirector.needsDecision` 的第一句是

```java
if(r.plan==null)return true;
```

指纹闸门（`decisionFingerprint`，为了不在没变的情形里重复问而存在的那个东西）
**只管还有计划的人**。计划一结束就无条件再问一次——而 `rest` 排的就是一个会结束的计划，
于是 rest → 计划结束 → 再问 → rest，一圈 10 分钟。

`none` 反而是这里唯一便宜的答案：它设 `decisionRetryAfter`，安静 10–30 分钟。
**排了"休息"的人比答"没什么想做"的人贵一倍——这是反的。**

**下一条该定的规矩，和今天这条是同一条，只是高了一层：**

> 相遇有 `encounterFingerprint`，时机有 `askedOccasions`，
> **而花掉 95% token 的那个问句，在最要紧的那一种情况下没有闸门。**

### react 的 `none` 掉到了 0/24

同一跑：greet 23、join 1、none 0、invite 0（提供 11 次）。

这是反方向的同一个毛病。「绝大多数擦肩而过的熟人之间，是有一声招呼的」这句是当初
greet 太少时加的，现在 greet 96%，**"看见了，继续做自己的事"变成了新的死路**。
0/24 就该按 0 来读，不管它是往哪边倒的。`PromptBalanceTest` 钉的是两侧都在，
钉不住两侧的比例——**比例只能靠跑出来的数看**。

`invite` 0/11 也记在这里：挂到对的时机上了，仍然是 0。
一个可能的解释是它和 greet 不互斥——打了招呼之后在对话里照样能提那件事，
所以"专门叫他一起"这个选项没有独立的位置。这是猜测，下一跑该量的。

### 三层：反射 / 时机 / 叙事（2026-09-12 晚）

诊断跑量出 32.1% 的复读之后，架构该长什么样就清楚了。参照那张"叙事层在上、逻辑层在下"的图，
关键不是"上面挂了个模型"，而是**下面那一层自己会跑**——逻辑层不是模型的执行器，它是常驻的世界，
模型只在有叙事内容的地方被叫。

我们之前反过来了：**模型被叫来回答没有叙事内容的问题。**「你的计划结束了，房间里什么都没变，
接下来做什么」——这句话在一次六小时的跑里问了 78 遍，每遍都收到同一句话。

现在是三层：

| 层 | 谁在答 | 什么时候 | 成本 |
| --- | --- | --- | --- |
| **反射** | 规则重复本人上一次的决定 | 情形一点没变 | 0 |
| **时机** | `Occasions` | 认得出的那一刻 | 一次，两选一 |
| **叙事** | 模型 | 情形真的变了，或者有话要说、有账要算 | 贵 |

反射层（`ResidentSimulation.extendByReflex`）的边界是这条批次里最要紧的一句话：
**它只重复，从不决定。**

- 只接着做**本人自己选过**的事（`planFromDecision`）。规则自己安排的计划不许被顺下去——
  顺一件没人选过的事，就是规则在过日子。
- 只在**情形一点没变**时（`situationFingerprint`）。这个指纹比 `ResidentDirector` 那个更严：
  它还带上"此刻同一个地方还有谁"。**屋里多了个人就是变了。**
- 只有 `rest/read/study/work/make/observe` 这几件"自己的下午"。
  `tend/join/invite/celebrate/create/help` 一律不顺——那些指向别人或别人的东西，
  顺一件那样的事等于规则替人做了一个社交决定。
- 最多接着 **3 次**，然后无论如何重新问。四段休息已经一个多钟头；再往后，
  "什么都没变"就不再是不问一个人的好理由。
- 每一次都写进 `decisionTriggers`，记成 `reflex:<action>`。
  **"这镇上有多少是规则在自我重复"必须是一个随时查得到的数**——
  这个项目最贵的教训就是"一件我们做的事看起来像一件他们做的事"。
- 有人站到面前、有时机抛出来、天色变了、店关门了，任何一条都优先于顺下去。

还有一件反直觉的事被这个改动顺手修了：**之前最便宜的答案反而最贵。**
答 `none` 的人会安静 10–30 分钟；排 `rest` 的人 10 分钟后计划一结束又被问一遍。
这就是 `rest` 34.6% 对 `none` 1.6% 的真正来源——不是有人想休息，是复读被记成了休息。

### 距离在画面里和在规则里得是同一个单位

同一天查出来的另一件事，和 32.1% 是同一类：**两处各自算一套数，谁也不认识谁。**

小人以 72 px/s 走到目的地门口，然后**站在那儿等后端的倒计时跑完**
（`companion-scene.ts`：`if (travelling) target = ...door`）。
后端的 `travelSeconds` 用一张抽象的"街道坐标"表算，知夏家→咖啡馆是 **320 秒**，
而画面上那段路只有 809 像素、走完 11 秒。于是门口罚站 5 分钟。

**街道 816 像素宽，横穿它却要 5 分钟。** 这不是调参问题，是两套单位。

改法：距离表用前端真正的寻路器在真实碰撞世界上算一遍（不是估的），
烘进 domain 的一张纯常量表；`travelSeconds = 像素距离 ÷ 步行速度`（32 px/s，两边同一个常量）。
再加一道防漂移测试：前端重算距离，和 Java 里那张表逐对比对，不一致就红——
仓库里已有同类先例（走道的绘制和碰撞矩形必须逐像素一致，否则就是"看不见的墙"）。

结果是这道守卫刚落地就抓到两件真东西，**而且都不是它本来要抓的那件**：

**一、"锚点"写成散文，两边各读各的。** 我描述的是"花园框下缘中点"，
重算的人读成了"框中心"，于是 28 对里 12 对静悄悄差 2–23 像素——
看上去像手抄错误，其实一个字都没抄错。现在锚点不再用文字描述，
而是 `travelAnchor(location)` 这一个函数：**场景走向它，表按它量，测试按它复核。**
一处定义，三个读者。

**二、花园的落脚点在花坛里。** `placeCenter('garden')` 落在
`{1128, 329}`，正好压在两块苗圃障碍矩形之一上。寻路器对一个站不住的点返回空路径，
于是**所有去花园的人根本没走过——他们原地不动，直到后端把 place 一翻，人就出现在里面了**。
这个 bug 存在了多久没人知道，因为画面上"瞬移"和"走得快"很难分辨。
`travelAnchor` 现在把非门类的落脚点 `nearestStandable` 一下。

**三、来回两条路不一样长。** 寻路器有方向性，最大差 23 像素。
一张对称的表不可能同时精确匹配两个方向，所以表里存的是两向均值，
测试的容差是**从这个实测差值推出来的**，不是为了让数字过而放宽的。
23 像素在 32 px/s 下值 0.7 秒。

### 记忆系统在回声：51% 的召回是居民自己上一次说的话

问"给模型的上下文够不够"，量出来的答案不是"不够"，是"**大半是它自己的回声**"。
243 次决定、2017 条被召回的记忆：

| | |
| --- | --- |
| 召回里**居民自己写的** | **66%** |
| 其中 `reflection`（自己给自己的说法） | **51%** |
| 这些说法的平均 importance | **7.3——全世界最高**，压过亲眼看见的 5.7 |
| 拿到和上次**一模一样**记忆集的决定 | **44%** |
| `belief` 被召回的次数 | **0** |

两个原因，各修各的：

**一、检索的问题是用上一次的答案拼的。** 查询串是
`lifeIntent.purpose + r.plan.reason() + 在场的人`，而 `r.plan.reason()`
正是这个居民上一次被问时自己写下的那句话——并且每一句这样的理由都会被存成一条 reflection。
**于是问题由答案构成，然后把答案取了回来。**

Generative Agents 的检索查询是 agent 的**处境**。现在这里也是：
地点、手上这件事的动作和它指向的东西（世界事实，不是散文）、在场的人、屋里有什么、
显著体感，加上他自己给自己定下的长期方向（`lifeIntent.purpose` 是一个说出口的方向，
不是一次随口的托词，留着）。

**二、随口一句理由，importance 给了 7。** 比亲眼看见一件事（5）高，和真正要紧的事持平。
改成 4。不是删掉——confabulation 那条架构就建立在"居民自己的说法要被留下、要可检索"上，
这只是不让它压过他真正看见的东西。

### 「今天到现在你做了什么」——32.1% 的另一半

反射层挡住的是"情形没变还反复问"。但**居民被问到的时候，看不见自己的下午**。

`Context` 有 30 个字段，没有一个是"今天到现在你做了什么"。`explain` 那一问拿得到 `deeds`，
`decide` 拿不到。所以那 78 次逐字复读里有一半不是闸门的锅：

> 一个刚说过三遍「刚搬来，先在家里歇会儿」的人，是知道自己说过的。**我们的居民不知道。**
> 他不是在重复，他是每次都第一次回答。

现在 `ResidentState.todaysDoings` 记下每一段真正跑完的事（动作、地点、多久），
按本地日期翻页，合并成"读书 ×3，共 90 分钟"这样一行。

**记的是旁观者看得见的，和 `Deed` 同一条红线：没有为什么。**
为什么是他自己的事，留在他自己的记忆里、用他自己的话。

### 受控对照：三项改动，一项有效、一项小幅、一项把事情弄坏了（2026-09-12 深夜）

第一次验证跑我把对照做错了：换代码的同时换了 `worldId`，而 **worldId 就是种子**
（座位哈希、相遇顺序、走神全从它派生），而且那一跑还下了雨。
证据很直白——run B 里重复的理由全都以「雨声正好」开头，run A 是「刚搬来先在家里歇会儿」。
**两跑的重复由完全不同的主导条件驱动，压根不可比。** docs 里早写着
「换模型和换代码是一样的性质」，我自己违反了。

同种子重跑之后：

| | 改前 | 改后 |
| --- | --- | --- |
| 模型调用 | 360 | **284** −21% |
| input tokens | 1.37M | **1.03M** −24% |
| 决定数 | 243 | **202** −17% |
| 逐字重复 | 32.1% | **28.7%** −3.4pt |
| `rest` | 34.6% | **22.3%** |
| 同一记忆集 | 44.0% | **57.9%** ❌ |
| 召回中 reflection | 50.8% | **66.1%** ❌ |

**检索那一改，是我自己把它弄坏的，而且原因可以精确说出来。**

`relevanceFactor = 0.08 + 0.92 × relevance`。我把查询里的 `plan.reason()`（一整句中文）
换掉，其中一项是 `r.plan.action()`——**`rest`/`make` 这种英文 id，在中文记忆里一个字都匹配不上。**
于是几乎所有记忆的 relevance 都趋近 0，乘数一律 0.08，
**排序塌回纯粹的"新鲜度 × 重要性 × 层级"**——而 reflection 恰好是 tier 1、
而且是全世界写得最勤、最新的东西（一次决定写一条）。它把前十名全占了。

### 这不是权重问题，所以不该用权重修

加减权重修不了它：**有一种记忆的产出速度远高于其他任何一种，无论系数多少，它都会挤满窗口。**
所以改的是窗口本身——**召回里留出位置给"真正发生过的事"**：
居民自己写的 reflection 最多占一半，剩下的给他看见的、听见的。

三条边界：
- **信念不算在内。** `belief` 是这套记忆模型存在的理由——是他自己关于自己的结论，
  稀少而来之不易。把它和随口的说法一起限流，等于悄悄埋掉整个镇子正在被测量的那个东西。
- **绝不会让召回变少。** 没有别的可说时，就把他自己的话还给他，而不是还一个更短的列表。
- 这条限制是"窗口"层面的，不动打分——`CompanionRecall` 的三项加权一个字没改。

**一句话的教训：一次改三样，量出来的差就没法归因。** 这次靠的是改动之间刚好可分
（成本归指令、调用数归反射层、检索归检索），下次不该赌这个。

### 各学科具体量什么

**社会学（结构）**

| 条目 | 怎么量 | 现在能量吗 | 写死风险 |
| --- | --- | --- | --- |
| **规范 = 信念收敛** | ≥3 个居民各自独立在同一 key 下写下同向信念 | 要加指标，数据齐 | 低 |
| **分工** | 贡献在（人 × 项目 kind）上的集中度 | 能 | ⚠️ **高**：一旦加了 `kind × occupation` 加成，**这个维度就作废**，只能拿我们没写过的维度当证据 |
| **关系结构** | 已有 `relationshipAsymmetry`；要加"某几对稳定亲近、某几对稳定疏远"而非随机抖动 | 半 | 低 |
| **角色期待** | 服务请求是否偏向"上次真的做成的那个人" | 能 | 低 |

规范收敛这条有现成的反面可用：`MetricsExporter` 里已有 `sameTopicDivergence`
（同一件事被记成不同文本的比例），**把它翻过来就是规范形成**。

**权威与正当性** —— 这里有整套判据里最漂亮的一条：

> **契约只改变签字的两个人；正当性会改变第三个人。**

所以 `takeover` 之后不看当事双方，**看别人**：服务请求有没有改投新经营者？有没有人还去找旧的？
**只有旁观者的行为跟着变了才叫权威转移**，否则只是一纸私约。今天就能量，
而我们完全没写过"别人应该改投谁"。

另两条：授权被拒之后有没有后果（`work_rejected` 事件已有）；
承诺被违反之后有没有**我们没写过的制裁**。

**经济学（不用钱的两条）**

- **互惠**：A 帮过 B 之后，B 后来帮 A 的概率**高于**帮别人的概率。
- **稀缺下的排序**：两人同时要那个只有一个人能占的东西时，怎么解决、解决方式稳不稳定。

**哲学（自由与自我认识）**

| 条目 | 怎么量 | 为什么它是"好结果" |
| --- | --- | --- |
| **解释与事实的落差** | `explain` 写的账 vs `deed` 记录的事实，由**没参与设计**的 agent 盲判 | **落差为零反而是坏消息**——那说明居民是台账机器。"先做后解释"要成立，就得有一定比例的**真诚但不准确**的自述 |
| **同境不同择** | 同一个 `decisionFingerprint` 出现多次时，选择的分布 | 全同 = 自动机；全随机 = 噪声；**要的是中间那段**。这是"活着 vs 走时"的量化形式 |

`decisionFingerprint` 在 `ResidentDirector` 里已经有了。

### 盲测的社会版

沿用已有的盲测纪律（[04](04-decisions.md)：*执行的人必须没有参与过设计*）：

> **给一个全新的、没读过仓库的 agent 看一段时间线，只问一句："这个镇上有什么规矩？"**

- 它读出我们量到的 → **规范真的在文本里**，不只在我们的统计里
- 它读出我们**没**量到的 → 更好，说明我们的指标还不够
- 什么也读不出来 → 就是没做到，无论指标多绿

### 如果只立一条：互惠

理由：它同时是社会学（关系）、经济学（交换的起点）、以及"义务从哪来"这一支的共同底座；
**它不可能被一条规则写出来**（可以写"A 帮了 B"，写不出"B 后来自发地更愿意帮 A"）；
现有数据结构就能算；而且**它是契约的最小单位**——在任何人签任何东西之前，
社会先有的是"你欠我一次"。

而要让它有机会出现，需要的正是第三节那两样东西。**这条目标不是空悬的，
它直接指向下一件该建的东西。**
