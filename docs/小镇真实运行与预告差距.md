# 真实小镇与预告画面的差距（2026-09-07）

本次从 mac-dev 的数据库汇总、服务日志、日程生成与渲染代码核对，未运行测试套件。

## 为什么街上只有两个 NPC

数据库共有 6 座小镇、113 条 NPC 档案，每座都有 18 位固定居民，部分还有旅人。固定居民的节律均为 JSON 对象，4 位旧旅人的节律是 JSON null。

当前体验发生在上海时区凌晨。已有当日日程在 00:30 的 37 条位置记录全部在家。前端 `applyTownNpcs` 不生成在家居民的街道角色，小助与邮递员另有常驻角色，所以街上两个角色不等于数据库只有两个 NPC。

另一个实际故障是 JSON null 被反序列化为 Java null，导致 `/town/npcs` 报 500。上一轮空日程兜底只恢复接口，没恢复旅人的生活。本轮增加按真实档案修复旧作息的流程：只修复结构缺失的节律，持久化后清除该 NPC 今天及以后的日程缓存，保留历史记录与有效作息。

## 尚未达到预告表现的部分

1. **录制日程经过编排。** `trailer-data.mjs` 固定时刻为 17:45，居民被安排全天停留在咖啡馆、学院、公园等地点，且没有通勤段。真实系统的昼夜人流未通过该视频得到验证。
2. **真实外出过短且集中。** 当前算法按起居窗口均分 2–4 次外出，每次办完就回家，空档全部在家；17:30 的上述真实日程中，36 人在家，只有 1 人在公园。这会让傍晚广景也显得空旷。
3. **显示上限与真实人数不同。** 前端午间最多显示 12 人、傍晚 7 人、深夜 3 人，包含两位常驻角色；还要先排除在家的人。不能仅通过调大上限解决实际日程空档。
4. **缺少居民去向的解释。** 本轮增加“邻居的今天”，展示服务端下发的当前位置与下一次外出，避免把回家误解为加载失败。它不是额外生成演示人口。
5. **夜间可玩内容不足。** 目前没有与真实日程一致的夜间咖啡馆、晚归居民、串门等完整生活设计。晨昏切换只改变画面，不应假装能改变居民的真实时间。

下一阶段应先设计有个体差异的早晚作息和连续外出安排，再让设施动作与场所活动一致；用真实接口分别录制早晨、午间、傍晚、深夜的代表性画面。不要再用全天定点的演示日程作为生活模拟已完成的证据。
